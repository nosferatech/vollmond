# Review of the Vollmond MD proposal, Draft v0.1

Reviewed: `docs/draft/vollmond-proposal.md` as of commit `b7c8a52` ("initial proposal draft"), with the discussion it came from
(`docs/draft/markdown_discussion.pdf`) and the two intended first customers: `~/vampiredb/tickets` and `~/vampiredb/docs`,
plus Belfry (`~/belfry`) as a likely consumer.
Date: 2026-10-09. Section numbers (§) refer to Draft v0.1.

The second half, [Owner's responses and decisions](#owners-responses-and-decisions), records what the project owner decided on
reading this review. Draft v0.2 is written from those decisions.

---

## Summary

The core ideas hold up: files are the source of truth, the index is derived, IDs are opt-in, semantic operations carry node-level
version tokens, and conformance comes in levels. But v0.1 is mostly a refactor-and-merge engine. The agent-facing read and query
surface, which is the stated core requirement, is mostly missing. And it describes a Markdown dialect the first customers do not
use, and that GitHub does not render.

## 1. Fit with existing conventions

vampiredb already has a working dialect, and v0.1 would not parse it:

| | v0.1 assumes | vampiredb uses |
|---|---|---|
| Record metadata | YAML front matter | A header table, `\| **Status** \| In progress — prose \|`, in both tickets and design docs, parsed by `scripts/ticket-lib.sh` |
| Node IDs | `## Title {#id}` | `### 11.4 The tail <a id="tail-and-flusher"></a>`; `Minimal_Log.md` alone has 304 |
| References | `[[record#id]]` | Standard links relative to the citing file: `[§11.4](Minimal_Log.md#room)`, `../docs/design/Minimal_Log.md#room`. About 657 in docs, 255 in tickets, 9 in Rust comments |
| Record ID | `[a-z0-9][a-z0-9._-]*` | `Minimal_Log`, `+index`, `0171-long-slug` (the stable identity is `0171`, not the path) |
| Link labels | Preserved on rewrite | Derived: the `§11.4` text is regenerated by `scripts/docs.sh --fix-refs` |

These choices are not accidental. GitHub shows `{#id}` and `[[wikilinks]]` as literal text, so v0.1's "Level 0: readable by any
tool" breaks on the main human viewing path.

**Suggestion:** separate the *model* (tree, addresses, references, schemas) from the *syntax*, choosing for each format the
syntax that is already idiomatic there: standard Markdown links, explicit `<a id>` anchors or heading slugs, `$ref` in JSON
and YAML. Make standard Markdown links the default reference form: they render everywhere and agents write them unprompted.
That means rewriting relative paths, not store-root addresses.

Belfry's prototype is already an informal non-git implementation of the model: a ticket stored as title, ordered header rows and
raw body; byte-for-byte export; `--outline`, `--section`, `--max-chars`; `status:blocked` filters; exit code 3 on conflict.
Its read surface is a good template.

## 2. Inconsistencies in v0.1

1. **Addresses do not resolve under their own rules.** In §4.4, `contact` is a child of `ada`. Under §5.2's path walk,
   `persons/ada#contact` (used in §5.1 and §10.1) does not resolve; it would be `#ada/contact`. Either make IDs unique per
   record with a flat lookup, as HTML anchors are, or use paths throughout.
2. **The example record fails its own schema.** The §7.5 schema wants `contact` at the root with
   `additionalProperties: false`; the normalized tree has `ada` at the root and `contact` under it.
3. **`$body` is ambiguous.** "Up to the next heading of equal or higher level" includes subsections, which are also child nodes,
   so their text is counted twice. Distinguish a section's own prose from its whole subtree.
4. **Front matter fields and section IDs share one namespace**, and a collision is an error, so a `status` field next to a
   `## Status` section breaks.
5. **`$` in CLI addresses breaks shells.** `vmd get "persons/ada#contact/$body"` expands `$body` inside double quotes.
6. **Code is not covered.** §10.4 excludes code from rewriting, but vampiredb's code cites docs by anchor.
7. **Freshness checks are expensive.** Hashing every record on every use is slow; `git ls-files -s` and git's stat cache give
   blob SHAs almost for free.
8. **Renames meet a policy.** vampiredb's docs say "An anchor is never renamed or removed". The section-rename use case needs
   that rule relaxed, which a safe rename makes possible.

## 3. Agent ergonomics

The discussion PDF lists the right practices: size before content, filter at the source, field projection, default limits,
pagination. None are in v0.1. They should be the core read surface:

```
vmd outline Minimal_Log            # ids, titles, ~tokens per node, refs-in count; no bodies
vmd get Minimal_Log#room --body --max-chars 4000
vmd refs-to Minimal_Log#room --context 1
vmd query tickets 'status:open component:log-v3' --fields id,title,severity --sort severity -n 20
vmd check [paths]                  # grouped, capped, each error with a fix hint
vmd schema tickets                 # compact field summary with enum values
```

- **Why it matters:** `Minimal_Log.md` is 667 KB, roughly 165k tokens. It cannot be read whole; `outline` and `get #id` make it
  addressable. This is the strongest single argument for vmd.
- **Query language:** v0.1 disclaims one, but the index needs one. A Belfry-style `field:value` filter covers the common case.
- **Write path:** `tx begin` / `op` / `status` / `commit` costs several turns. Make "edit with normal tools, then `vmd check`"
  first-class, and keep semantic operations for refactors and remote backends, through one `apply` call.
- **Version tokens:** optional on the local CLI, required over a remote API. Node-level tokens let two agents edit different
  sections of one record without conflict.
- **CLI over MCP:** a CLI plus a short skill file costs nothing until used; MCP tool schemas are paid for in every session.

## 4. Git

- **Use the git blob SHA as the record version token.** It is computable anywhere, and GitHub's Contents API uses the same SHA
  for optimistic-concurrency writes.
- **Defer Level 3.** Custom merge drivers run only in local git, never in GitHub's merge button or merge queue.
- **Validate in CI, not only in hooks.** Hooks are not installed by `clone` and do not run for commits made through the API.

## 5. An app on AWS reading and writing a GitHub-hosted store

- **Reads:** publish the index (and the content) on push rather than query GitHub live. A push triggers an incremental re-index,
  the result goes to S3, and the site reads from there.
- **Writes:** GraphQL `createCommitOnBranch` takes a required `expectedHeadOid`, so it is a multi-file atomic commit with
  compare-and-swap, which is the transaction model. Limits: branch protection, GitHub's content-creation rate limits, and a
  commit per change. Validation must run in the app before it commits.

## 6. A git-compatible service over a database

1. Git-like semantics through vmd's own API: moderate.
2. A database-to-git mirror: one direction is moderate; two-way sync is hard.
3. The git wire protocol over a database: doable with JGit DFS, libgit2 ODB/refdb backends, dulwich or go-git, but read-only
   clone takes weeks, push with validation more, hardening months. Every record write also rewrites tree objects up to the root,
   and all writers contend on one ref.

**Recommendation:** make the vmd backend contract the interface rather than the git protocol, with a local working copy
(`sync` / `push`) so agents keep their shell tools.

## 7. Phasing

Read side first (parsers, index, `outline` / `get` / `refs-to` / `query` / `check`), then refactors (`rename`, `mv`), then the
remote contract and publishing. Defer staged transactions, the merge driver and semantic diff.

### Corrections from reviewing the draft

An adversarial review of Draft v0.4 before merging found places where applying the decisions left a rule unsound. They were
corrected in the same round, without new decisions:

- `@key` names a computed key that vmd's validator evaluates natively, never a member added to the instance, and is allowed only
  on lists of sections; a JSON Pointer such as `"/@key"` names a literal member.
- Whether a record is readable never depends on its schema. Inside a field's value, a `$` member other than `$ref`, `$anchor` and
  `$tags` is data, and a root `$schema` member is stored data that vmd does not interpret. *Reversed by U12 (Draft v0.11): a
  record's readability now depends on its schema in one way, since readers refuse the records of a collection whose schema
  cannot be used; what the schema allows still never decides it.*
- A duplicate at a level the schema declares `type: map` is an error in either uniqueness mode.
- Section members of the wrong type, a section without a title and a malformed anchor element are structural errors.
- Unsupported HTML in a heading contributes its text but not its tags to the derived anchor.
- A retitle rewrites references to every node whose derived anchor it changes, `check` reports references whose target moved
  since the previous index and live anchors that shadow an alias, and `rename` and `mv` refuse while records fail parse.
