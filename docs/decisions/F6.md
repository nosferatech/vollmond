## Question

On [C16](C16.md) the owner asked for an escape hatch that makes a link match only explicit anchors, and noted it might be good
practice anyway. A fragment such as `#done` has to keep working on GitHub, where it already goes to the element with that id, so
new syntax inside the fragment would break GitHub navigation. How should a link say: explicit anchors only?

## Options

- **(a) A store setting plus a lint, no new syntax.** Recommended. A collection or store setting
  (`references: explicit-anchors-only`) makes references there resolve explicit anchors only; strict mode warns about any
  reference through a derived anchor; `vmd normalize` adds an explicit anchor to the target heading and rewrites the link. Links
  stay plain GitHub links.
- **(b) A marker in the fragment.** For example `#!done`. Self-describing per link, but GitHub cannot follow it, and every
  renderer shows a broken link.
- **(c) Only the lint.** Chosen, refined by the owner's note. No setting. Strict mode warns and normalize converts, but nothing
  guarantees a link cannot silently retarget to a derived anchor.

## Decision

(c), refined. No store setting and no normalization command. In YAML and JSON, a reference's schema can require an explicit
anchor as its target (`x-vmd-ref` with `anchors: explicit`), which the owner calls best practice for stores used as databases.
In Markdown a link stays plain, and `vmd check` warns about references through derived anchors, as a lint only. Whether a
Markdown link can carry an invisible attribute that says the same is open question 6 of Draft v0.4.

## Why

The owner's reasons: references of different cardinality already exist in YAML and JSON, so a constraint requiring an explicit
anchor fits there, and it is best practice when the entries are treated as a database; in Markdown, links typically do not point
to anchors, so if strong targeting is rare the syntax can stay as it is; and normalization is to be avoided, since a user who
wants to pass the linter can fix their data themselves. The card recommended (a) because it gives the guarantee without breaking
how links render; (b) breaks links on GitHub and in every renderer.

## Owner's note

> So, we already support different cardinality links (at least in yaml and json) right? So adding the constraint that it
> requires explicit anchor (either on schema level or on the link itself there), should be possible.  And I think that when
> treating those entries as database, it would be the best practice to always use this constraint.
>
> The markdown case is more complicated. We can expect links typically not point to anchors. But there might be cases, where user
> may want to make strong link targeting (because in this particular place, it really matters for it to point properly, and
> never be confused with possible auto slugged duplicate). If this case is very unlikely, then we can probably just leave the
> syntax as is. But hypothetically speaking: is there a way to put extra tags on attributes on markdown links that don't affect
> rendering?
>
> As for lint vs implicit normalization. I'd stay away from normalization, if user want to pass linter, they can fix their data
> themselves.
