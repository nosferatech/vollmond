## Question

§5.8 says the conformance suite tests the round trip as a property, meaning for many generated values. Generating values takes
code, and the suite holds only data. Separately, §19.2 put the serializer in no profile, so it was unclear which implementations
must pass `round_trip` cases (suite questions 13 and 14). For example, must a read-only Python port that never writes files pass
round-trip cases to claim the Read profile?

## Options

- **(a) Own property tests; suite examples under Write.** Chosen, as recommended. Each implementation runs the property test in
  its own tests (fast-check in TypeScript, plan §1.2). The suite holds fixed example round trips and the values that cannot be
  represented, and `round_trip` cases need the Write profile, since the canonical serializer arrives in I4. A read-only
  implementation is never asked to serialize.
- **(b) Same, but under Read.** Every reader must also serialize, which makes a read-only port or a published-index client bigger
  than its job, and `round_trip` cases fail for TypeScript until I4 delivers the serializer.
- **(c) The suite describes a generator.** A language-neutral description of values to generate, which every runner executes.
  Property testing is uniform, but the suite gains a small language of its own, against its data-only rule.

## Decision

(a). Each implementation has its own round-trip property tests, and the suite holds example cases under the Write profile.

## Why

The card's reason: as the suite recommends for questions 13 and 14, merged because both concern `round_trip` cases. (b) makes
every reader serialize; (c) gives the data-only suite a language of its own.
