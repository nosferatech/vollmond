## Question

A record has explicit anchors (`<a id>` in Markdown, `$anchor` in data) and derived ones (heading slugs). They can collide, when
one heading's explicit id equals another heading's derived anchor; GitHub then emits two elements with the same id, and a browser
goes to the first one on the page. §9.2 checks duplicate anchors but did not say whether this counts, and the first step of an
address (§7.3) looks up both kinds (suite question 11). For example, a record has `## Notes` followed later by
`## Summary <a id="notes"></a>`: which section does `file.md#notes` reach?

## Options

- **(a) One namespace; a collision is a duplicate anchor.** Chosen, as recommended. `vmd check` reports `duplicate-anchor`, an
  error under the strict default, and the author renames one of the two. Every anchor names exactly one node, and GitHub and vmd
  never disagree about where `#notes` lands. Adding an explicit anchor can create an error that points at a heading elsewhere in
  the file, and the hint names it.
- **(b) Separate; the explicit anchor wins.** No error. In vmd `#notes` reaches Summary, while on GitHub the browser goes to the
  first heading, Notes. A link that lands in two different places depending on the reader.
- **(c) Separate; first in the document wins.** Matches the browser, but it is "first occurrence wins", which the decision log
  rejects, because inserting a heading earlier in the file silently retargets existing links.

## Decision

(a). Explicit and derived anchors share one namespace, and a collision is a duplicate anchor. The owner added that an escape
hatch making a link match explicit anchors only would be good practice, which the follow-up [F6](F6.md) took up.

## Why

The card's reason: as the suite recommends; it is the only option where a link means the same thing on GitHub and in vmd. (b)
sends one link to two places; (c) is "first occurrence wins", which an earlier decision rejected.

## Owner's note

> We may need to offer some escape hatch here. If there was a way to write a link that explicitly stated to match only explicit
> slugs, it could be such escape hatch, and it might actually be a good practice anyway.
