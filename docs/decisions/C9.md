## Question

A Markdown record saved with Windows line endings (CRLF) has multi-line `$body` text. Does the value view keep `\r\n`, or read
each line break as `\n`? The answer decides whether the LF and CRLF copies of one record are equal and have the same node version
tokens (suite question 7). For example, git on Windows with `core.autocrlf` checks every file out with CRLF, so the same section
body is `Line one\r\nLine two` there and `Line one\nLine two` on Linux CI.

## Options

- **(a) Read as `\n`; edits keep the file's own endings.** Chosen, as recommended. Both copies have identical value views and node
  versions, so a Windows checkout and Linux CI agree, and an edit based on a version read on one machine applies on the other.
  File versions (git blob ids) still differ, as git's own do. An edit writes new text with the file's existing line ending, so a
  CRLF file stays CRLF. The Markdown parser normalizes line breaks when it slices `$body` from the file; YAML already does this
  for block text, and an explicit `\r` escape inside a JSON or quoted YAML string is content and stays.
- **(b) Keep the bytes as found.** Slicing is simpler, but every multi-line value and node version differs between the two
  checkouts. Automatic rebase (§11.6) then sees every section as changed, and a query or a fixture that matches a line break gives
  different answers by platform.

## Decision

(a), with the owner's note. The value view reads CRLF as `\n`. Edits keep the file's own line endings where the backend keeps
the file, and a backend is not required to preserve `\r\n`, since some may not and some could even convert `\n` to `\r\n`.

## Why

The card's reason: as the suite recommends; without it, git's line-ending conversion on Windows would change every multi-line
value and every node version. (b) makes values, node versions and query results differ by platform.

## Owner's note

> And we don't promise that backend will keep \r\n. Some backend may, some may not. And some backends could even convert to
> \n to \r\n.
