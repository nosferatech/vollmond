## Question

JSON Schema handles arrays of keyed items, such as sections, poorly. The owner asked for an extension that makes heterogeneous
`[{key: ..., value: ...}]` arrays easy to describe, for sections and any similar data. And where do the keys of items in plain
data arrays come from: `$anchor` only, or also fields that a schema names?

## Options

For the keys of data arrays, as the session put them with a perf-run example:

- **(a) Keys from `$anchor` only.** No schema is needed to resolve, but every item needs an anchor, usually repeating its name,
  and nobody writes YAML that way.
- **(b) Keys declared by the schema**, in the Kubernetes style (`x-vmd-list: {type: map, keys: [name]}`). Chosen, as the session
  recommended. The data stays as written; the cost is that resolution depends on the schema.

For the extension, the session combined Kubernetes' `x-kubernetes-list-type` / `x-kubernetes-list-map-keys`, choosing a subschema
by a key's value (OpenAPI's and JSON Type Definition's `discriminator`, `propertyDependencies`), and `ajv-keywords`'
`uniqueItemProperties` into one keyword. Other options for the extension: Not recorded.

## Decision

A schema extension modeled on Kubernetes' `x-kubernetes-list-type` / `x-kubernetes-list-map-keys`:
`x-vmd-list: {type: map | multimap, keys, required, items (per-key schemas), additional}`. It applies to any array, sections
included, and compiles to standard JSON Schema 2020-12, except uniqueness over undeclared keys, which needs a custom keyword. Keys
in data arrays may be declared by the schema (option (b)): resolution depending on the schema is accepted, since queries and
validation rely on schemas anyway. `$anchor` works without a schema.

## Why

The owner's reason for accepting (b)'s cost: any query or validation should rely on the schema anyway, so it is not a difficult
ask. The session's mitigations: exact paths never depend on the schema, and the index stores each reference's resolved exact
path, so `vmd check` reports a reference whose target moved after a schema change. (a) makes the data redundant.
