## Question

Question 6 of the phase I1 design (#59), item 6 of card K: where does the slug rule's Unicode data come from?

## Options

- **(a) The runtime only, with the probe.**
- **(b) Generated tables for all of §6.3, NFC included.**
- **(c) Tables for the properties and the lower-case mapping, NFC from the runtime.** Chosen, as recommended. (b) if a runtime's
  NFC is ever found to differ.

## Decision

(c), through card K's option (b), which accepted every recommendation but question 3's: Unicode properties and lower-case
mappings come from tables generated from UCD 17.0.0, and NFC from the runtime. NFC moves to tables too if a runtime is ever
found to differ. It is an implementation choice that the design records, not a change to the specification.

## Why

The design's reason: (c) removes the runtime from the rule where versions differ most, at a small size. Its section 4.1 gives why
not the runtime alone (a): `engines` admits every Node 24 release, some with older ICU, later Node majors move to Unicode 18, and
browsers have their own data, so a character unassigned in one version is removed by step 5 there and kept in another, and one
heading gets two anchors. (b) is kept in reserve for a runtime whose NFC differs.
