## Question

[F9](F9.md) moved `$key` out of the value into a metadata envelope. The draft's shape was `{value, meta}`, where `meta` has the
path, the address, the key (absent for the root), the anchors with their kinds, the version, the source location, and `nodes`
(metadata for every section below). This is an API contract, so it was worth confirming: what is the shape of what a read
returns? The question came from the independent review of #50 (Draft v0.4).

## Options

- **(a) As drafted, plus issues, with nodes opt-in.** Chosen, as recommended. The envelope also carries the issues attached to a
  readable record (the natural home for validation errors under F1), and the per-section `nodes` map appears only on request,
  which keeps reads small for agents.
- **(b) As drafted.** Issues are fetched with `check` only, and every read includes metadata for every section below.

## Decision

(a), reframed by the owner's note. Metadata are computed fields, not part of the data: like `rowid` in some SQL databases, they
are not in `SELECT *` and cannot be written, but they can be selected explicitly. A plain read returns the stored data only, so
a read and write round trip is exact. A caller that needs computed fields, such as a validating reader or a writer that needs the
version token, requests them explicitly, with the read or later by address, and then gets them as drafted, with `@issues` added
and `@nodes` only on request. The computed fields have the names of VQL's pseudo-fields, so requesting them and selecting `@key`
in a query are one concept. Writes return the new version token, so editing needs no extra round trip (§5.10, §10.3, §13.2).

The session added the last two points, the shared names with VQL and the version token returned by writes, and asked the owner
to say if either went too far. Applying it added three computed fields (`@refs`, `@collection`, `@depth`) so that the computed
fields and VQL's `@` fields are one set, and the independent review then aligned their meaning in VQL: `@issues:>0` compares the
list's length and `@anchors:x` matches by name. A write also returns the new versions of the target's parent sections.

## Why

The card's reason for (a): issues travel with the data they describe, and the default read stays economical. The card's
consequence for (b), not a reason it gives against it: issues come only from `check`, and every read carries metadata for every
section below. The owner's reframing keeps a plain read exact for a round trip, since computed fields are never part of the
data.

## Owner's note

> The spirit of the metadata envelope, is that those are effectively computed fields. I think we can treat them similar to any
> other computed expression. There are not really part of data, but can still be queries, if needed.
> So a regular reader that just want to read data, will just return the "official" data (so that read-write roundtrip is
> correct).
> However, a validating reader, may also request (either up front or during reading) the computed values and use them for it's
> purposes.
> It's like rowid() in some SQL databases, its not part of SELECT *, can't be written to, but can be explicitly selected.
