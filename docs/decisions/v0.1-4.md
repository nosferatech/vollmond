## Question

The owner's own generalization, answering the review's list of metadata carriers: for addressing and querying, should data
fields and Markdown sections at the same level be equivalent?

## Options

- **(a) Data fields and Markdown sections at the same level are equivalent.** Chosen: `name: "stuff stuff"` is analogous to a
  section `# name` containing `stuff stuff`.

Other options: Not recorded.

## Decision

(a). For addressing and querying, data fields and Markdown sections at the same level are equivalent. Left to settle: whether an
address that resolves to a section returns its contents or the whole section, and whether a JSON or YAML representation of
Markdown can round-trip.

## Why

Not recorded.

## Owner's note

> The generalization I'd like to propose, is that for addressing/querying the "metadata" blocks should be considered on equal
> footing as the markdown. Where if on the same level yaml/json fields should be considered similarly to markdown sections:
>
> ```
> name: "stuff stuff"
> ```
> would kind of analogous to:
> # name
> stuff stuff
>
> Some things to sort out is whether querying a "path" that resolves to a markdown section, should return just the contents or
> the entire section. It the latter, then the equivalent json yaml would need to look a bit different to allow for natural
> representation of nested sections.
>
> So perhaps one of the things we need to figure out, if there is a reasonable json/yaml representation of markdown that
> rountrips.

## Applied in

Draft v0.2 (`5998461`), where a field and a section with only text had the same value. [v0.2-6](v0.2-6.md) replaced that with
"a record is a section": the equivalence moved from values to addresses, so `status: Open` and `## Status` no longer have the
same value, but the same semantic step reaches both.
