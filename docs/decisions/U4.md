## Question

§14.3 put the local index, a cache, in `.vmd/cache/`, never committed. The independent review of the I2 design showed that
reading anything in a checkout as a cache lets a pull request commit a forged one, with `git add -f` past a `.gitignore`, saying
that a broken record is valid, and make a gate's `vmd check` (§9.4, pattern B of §16.3) pass a broken store. An entry is a claim
about a file's bytes that `check` believes without parsing them, and a file's blob id and a released vmd's implementation id are
both public. Where does the cache live?

## Options

- **(a) Always in the per-user cache directory.** Chosen, as recommended. `~/Library/Caches/vmd/` or `$XDG_CACHE_HOME/vmd/` (or
  `~/.cache/vmd/`), for every store, with or without a `.vmd/` of its own. Entries are content-addressed and shared by every store
  and worktree, with one snapshot per store, eviction under 512 MB, and a global `--no-cache`. Nothing in a checkout is read as
  cache, and reading vampiredb's `docs/` writes nothing there (K3). §14.3, §12.1 and §17 change.
- **(b) `.vmd/cache/` in the store, and the per-user directory only for a store read with `--config`.** What the first version of
  the design proposed. It reads the checkout as cache, so it needs a defense, and the one proposed, a MAC, does not hold up.
- **(c) No persistent cache unless `--cache DIR` says where.** As stated.
- **(d) A MAC on each entry**, under a key kept in the per-user directory, for a cache in `.vmd/cache/`: the first version's
  defense for (b), rejected by the design (§6.2.1).
- **(e) Ignoring cache files that git tracks**: rejected by the design.
- **(f) Re-verifying entries by parsing them**: rejected by the design.

## Decision

(a). The cache is never in the store: it lives in the per-user cache directory, content-addressed and shared by every store and
worktree, with one snapshot per store's real path, eviction under 512 MB, and a global `--no-cache`. A committed `.vmd/cache/` is
an ordinary ignored directory, never read. The guidance for `vmd check` in CI is to restore no vmd cache in a gate, or to pass
`--no-cache` there.

## Why

The card's reason: "Removes the attack instead of defending against it, with no extra mechanism." The design adds that, with the
cache in the per-user directory, what the cache trusts is exactly what the user's home directory holds, written by the user's
own vmd, and a forged entry would need a write there, which could as well replace vmd itself.

The design's reasons against the MAC: a cache that always lives in the per-user directory never reads the checkout, so committed
entries are harmless without a MAC; a CI restore of the per-user directory brings the key along with the entries, which defeats
it; a restore of `.vmd/cache/` alone misses every entry, so the MAC protects only where the cache is useless; and relying on
"never cache the key" is the same weakness as relying on a gate to pass `--no-cache`. Ignoring files that git tracks needs git and
misses everything that reaches the directory another way, and re-verifying entries by parsing removes what the cache is for. (b)
reads the checkout as cache with no defense that holds.

Why (c) lost: Not recorded.

## Owner's note

On the I2 design card ([I2-design](I2-design.md)), not on U4:

> This review brought a question on where the index lives? And I think answer is "depends". In case of lightweight setup, where
> the backend is pure simple git repo, the index should live locally, as otherwise it would cause merge conflicts.
> However, for more advanced git setup (a custom merger, lambda, actions etc) the index should live somewhere in the backend,
> either git repo, or some other configured storage.
