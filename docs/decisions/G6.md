## Question

The owner had decided that warnings are configurable by issue code, within limits the issue-code appendix sets. The draft's
limits: structural and operation codes are fixed, validation errors can never be lowered, and only warnings can be set to `off`,
`warning` or `error`. The reviewer's concern: vampiredb's docs have existing broken links and other issues, so this could block
adopting vmd step by step (rollout R1). Which issue codes may a store configure, and how far? The question came from the
independent review of #50 (Draft v0.4).

## Options

- **(a) Validation errors may be lowered to warning, never off.** Recommended. A store adopting vmd can keep `check` green while
  it fixes existing problems, and still sees every issue. Structural and operation codes stay fixed. Gate mode can require the
  defaults.
- **(b) As drafted: validation errors are fixed.** Chosen. Strictest; an existing store with broken links fails `check` until
  every one is fixed, so adoption is all or nothing.
- **(c) Everything except structural codes may be turned off.** Most flexible; a store can hide problems entirely.

## Decision

(b), against the recommendation. Validation errors cannot be lowered. To adopt vmd step by step, a store fixes the data, relaxes
the schema so that it permits the offending data, or comments out the offending links; adoption goes by relaxing the schema
first and tightening it later (Appendix D, R1 in §22).

## Why

The owner's reason: validation errors need to be fixed, and a user who does not want to fix them all at once has other means
than lowering them, relaxing the schema or commenting out the links. The card's reason for (a) was that real stores could adopt
vmd incrementally without hiding anything; the log's answer to that concern is that adoption still goes step by step, by
relaxing the schema first and tightening it later. Why (c) lost: Not recorded.

The session's follow-up made the second remedy work: the draft had never said that a link inside an HTML comment is not a
reference; §8.1 now does, citing CommonMark. JSON has no comments, so there the remedy is to remove the reference or replace it
with a plain string, and relaxing the schema does not clear a dangling link.

## Owner's note

> the validation errors need to be fixed. If user doesn't want to fix them all immediately, then should use alternatives, like:
> - relax the schema, to permit offending data
> - "comment out" the offending links.
