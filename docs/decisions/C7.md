## Question

vmd reads YAML 1.2, where `2026-10-09` and `yes` are plain strings. Many tools still read YAML 1.1 (PyYAML, Ruby's Psych used by
Jekyll, js-yaml before version 5) and turn them into a date and a boolean. §4.4 told the serializer to quote such strings and gave
three examples; the survey found the set much larger, different from reader to reader, and that the `yaml` library's writer
quotes none of them by default (survey §4.1 and §7.2). For example, a ticket says `answer: no`: vmd reads the string `no`, PyYAML
reads false, and a Jekyll page shows false. The survey also found that `ruamel.yaml` reads `2026-10-09` as a date even in YAML 1.2
mode. Which YAML strings must the serializer quote for older readers?

## Options

- **(a) Quote the full list, and warn in strict mode.** Recommended. The serializer quotes every string any common reader takes
  for something else: dates and date-times, `yes`, `no`, `on`, `off`, `y`, `n`, `true` and `false` in any case, YAML 1.1 numbers
  (`017`, `0b101`, `1_000`, `1:30`), YAML 1.2 numbers (`0o17`, `0x1F`, `1e3`, `.inf`, `.nan`), `null`, `~`, the empty string,
  `<<` and `=`. `vmd check` warns about unquoted ones in strict mode. vmd needs its own quoting table on top of the `yaml`
  library, and files it writes read the same in every tool.
- **(b) Quote only what YAML 1.2 misreads.** This is the `yaml` library's default, so no extra code. vmd and modern tools read the
  files correctly, but a Jekyll site or a Python script using PyYAML sees `no` as false and `2026-10-09` as a date, and nothing
  warns about it.
- **(c) Full list, but no check warning.** What vmd writes is safe everywhere, but hand-written front matter such as
  `answer: no` is never flagged, so the problem shows up only when another tool reads the file.

Chosen: neither. The owner answered Other, with a note about format versions, which the session read as a different question.

## Decision

No option was taken on this card. The session read the owner's note as being about older versions of vmd, while the card was
about other YAML tools, and asked again as [F3](F3.md), whose answer is the decision. The versioning point of the note became
its own card, [F4](F4.md).

## Why

The card's reason for (a): the survey's proposed §4.4 wording; the cost is a small table in core, front matter is read by many
tools besides vmd, and a strict-mode warning is the only way hand-written files get caught. The owner's note answered a
different question, so the reasons were settled on F3.

## Owner's note

> It is plausible that stores will be configured at different times for different versions. And that data will exist, and may
> or may not get updated to a newer version.
> Same goes for clients (particularly writers, but readers have similar problem I guess), they may have been written using
> version X, while the store was defined or upgraded to version Y. Ideally it should work. So a client would normally declare a
> version, and submit a payload, and that should get validated against version X, and then on the fly transcoded to version Y.
> And similarly for the reader.
> How can we know what protocol version is used? Ideally, that would be provided either in the client setup (.gitignore version
> settings for git-based repo, or a setting on the "connection-string" when doing database-style connection.
