## Question

Step 2 of the slug rule, as [F5](F5.md) gave it, normalizes to NFC and then drops invisible characters. `e`, U+FE0F, U+0301
looks like `é`, but normalizing first keeps `e` and U+0301, since the variation selector blocks composition, so its anchor
differs from a plain `é` heading's. The slug fixtures (#55, question 7) pinned the order as written in
`edges/nfc-before-ignorable-removal`; by the session's own check, which computed both orders for every record, only that record
depends on the order.
Should step 2 normalize after removing the invisible characters?

## Options

- **(a) Remove the Default_Ignorable characters first, then normalize,** so headings that look the same get the same anchor; the
  case then expects `é` (U+00E9). Chosen, as recommended.
- **(b) Keep the order as written:** NFC first, so `e`, U+FE0F, U+0301 keeps `e` and U+0301.

## Decision

(a), as card H5's option (a), accepting every recommendation. Step 2 removes Default_Ignorable characters first, then normalizes
to NFC. This changes the rule that Draft v0.4 stated and the I0.7 fixtures pin: `e`, U+FE0F, U+0301 now gives `é` (U+00E9), so
that an invisible character cannot keep two headings that look the same apart. The fixture case (`edges.cases.json` of #55) is
updated after #55 merges.

## Why

The card's and PR's reason: an invisible character cannot make two anchors that look the same differ, which (b) allows. The
card's note: each recommendation keeps vmd strict and its output readable back, and none contradicts an earlier decision.

## Applied in

Draft v0.5 (#57, `d0d1424`), §6.3 step 2; the review of #57 confirmed that the case gives `é`. [O5](O5.md) later made step 2
also remove the code points unassigned in Unicode 17.0.0 before NFC (Draft v0.10).
