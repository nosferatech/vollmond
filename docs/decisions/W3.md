## Question

Draft v0.12 (#96) applies the owner's answers to cards W1, W2, X and Y. Where an answer left a detail open, the spec agent wrote
what the code already does, or what follows most naturally, and marked each record "Agent's reading, for the owner to confirm".
The card lists eight such details:

1. Odd files in the schema folder ([X1](X1.md)). In a store's own `.vmd/schema/`, a symbolic link, a FIFO or an empty directory
   counts as a missing schema (`schema-invalid`), because the storage layer reads them as absent; a directory with files in it is
   `storage-failed`; beside a `--config` file, a FIFO or a directory is `storage-failed`. The card left open: "should a FIFO
   inside a store be `storage-failed` too?"
2. An unclosed data block in the wrong place ([P2](P2.md)) gets `syntax-error` as well as `data-block-misplaced`, as Appendix D
   already implied.
3. `@collection` for a record in no collection ([S5](S5.md)) is absent, not null, as `@key` is, and the same holds when two
   collections claim the record.
4. Writes beside an unusable schema ([W2](W2.md)) are refused in every validation mode, by whatever validates the write, the
   client library included.
5. How inline nesting counts toward the 256 limit ([Y1](Y1.md)): separately from the nesting of lists and quotes, within each
   block or data `$title`, starting at 1, with emphasis, strong, strikethrough and links counting. The card names strikethrough as
   the agent's addition to the owner's "emphasis or links".
6. The run limit in headings and titles ([Y2](Y2.md)): each heading and each data `$title` gets its own 4,096-run limit, and going
   over is a `syntax-error` on the record.
7. Bounded reads (from the configuration pull request, #91): the storage contract's `read` takes an optional byte limit, a file
   over it is refused by its size before it is read, a file that grows while it is read is refused too, and the limits are 1 MiB
   for configuration and schemas and 16 MiB for a record. The decision log of Draft v0.12 lists it as an alignment.
8. How the records link: Y1 and Y2 mark [P1](P1.md) as superseded, and [Y3](Y3.md) marks [P3](P3.md) as superseded, each
   extending the earlier rule in the same direction. P1's limits all still stand.

Confirming makes them decided; on the card, any the owner rejects becomes its own card.

## Options

- **(a) Confirm all eight.** Chosen, as recommended. The card: "The records drop the label, and nothing in the code changes."
- **(b) Confirm, except what the note says.** The card: "Each exception becomes its own card; the code keeps today's behaviour
  until it's decided."
- **(c) Discuss first.** The card: "The readings stay labelled in the records."

## Decision

(a), with a note that answers item 1's open question: "fifo's in the store should cause failure". A FIFO anywhere in the store is
a failure, `storage-failed`, not a missing file, in a store's own `.vmd/schema/` too, where Draft v0.12 read it as missing
(`schema-invalid`). Everything else the card states is confirmed: items 2 to 8, and of item 1 that a symbolic link or an empty
directory in `.vmd/schema/` counts as a missing schema, that a directory with files in it is `storage-failed`, and that beside a
`--config` file a FIFO or a directory is `storage-failed`. The records that hold the readings (P2, S5, W2, X1, Y1, Y2 and Y3) and
the decision log's alignment of the bounded reads say so. The storage contract (§11.2) states the FIFO rule. That makes the card's
"nothing in the code changes" untrue for item 1: the backend reads a FIFO as missing today, and the change follows in a later pull
request.

**Agent's reading, confirmed by the owner on [W4](W4.md) (items 1 to 3, and 10 for the last point).** Three details the note
leaves open, which Draft v0.13 states as follows:

- What the rule means for a listing: `list` and `grep` leave a FIFO out with a `storage-failed` issue of severity `error`, as they
  leave out a file they cannot read, and the operation still succeeds (§11.2, §12.3). A path that vmd ignores (§3.3), which is
  neither a record nor an asset, raises no issue in a listing, while a read of it by name, such as a schema in `.vmd/schema/`,
  still fails.
- Sockets and devices are treated as FIFOs are, in the store and beside a `--config` file, since the note's reason, "the don't
  belong there", holds for them too: anything that is not a regular file, a directory or a symbolic link.
- That this amends X1's applied rule for a FIFO, in the same direction, more files that cannot be read being `storage-failed`, and
  so supersedes X1, as [Y1](Y1.md) superseded P1, is this record's reading; the card does not say so. X1's decision stands.

## Why

The card's reason for the recommendation: "Each matches what the code does today and what the existing rules imply. Number 1's
open FIFO question can wait until a FIFO in a store causes trouble." The owner's note decides that question now, for its own
reason: FIFOs do not belong in a store, so meeting one is a failure.

Why (b) and (c) lost: Not recorded.
