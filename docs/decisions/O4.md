## Question

Under `--json`, the CLI foundation (#74) printed a usage error, a missing store and the runtime's Unicode warning as text on
stderr, while a configuration error was JSON on stdout, so agents had to parse text. What does `--json` do with failures that are
not outcomes?

## Options

- **(a) Every failure is an outcome-shaped JSON object on stdout**, with new operation codes `usage-invalid` and
  `store-not-found` in Appendix D. Chosen, as recommended.
- **(b) Keep them as text on stderr, as #74 printed them.** Agents then have to parse text.

## Decision

(a), with card O's option (a), accepting every recommendation. Under `--json`, every failure is an outcome-shaped JSON object on
stdout, usage errors, a missing store and the runtime's Unicode warning included (§12.2, §12.3): `{"ok": true, "value", "issues"}`
on success and `{"ok": false, "issues"}` on failure, as the CLI's outcome type. Appendix D gains the operation codes
`usage-invalid` and `store-not-found`; an unreadable or missing `--config` path is `config-invalid`, an unreadable working
directory is `store-not-found`, and an internal error, a bug, is the one failure exempt from the issue codes. The card asks for
the runtime warning as an issue but names no code for it, and every issue needs one, so the draft adds a third,
`unicode-runtime-older` (a warning); that code and its name are the agent's, confirmed by the owner on [W12](W12.md)
(2026-10-20), its item 1.

## Why

The card's reason: agents should not have to parse text. For the card as a whole: each rule makes the CLI predictable for agents
and keeps anchors stable across Node versions.

## Applied in

Draft v0.10 (#78, `d1e0a60`), §12.2, §12.3 and Appendix D; the read commands (#84, `2fe7dc4`) follow it. The code
`unicode-runtime-older` still waits for the owner's confirmation.
