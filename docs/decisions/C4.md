## Question

JavaScript, which `@vollmond/core` uses, reads every JSON number as a double. §4.2 required integers up to 2^53−1 to be exact
and every other number to be held "at least as a double", and forbade silent rounding. The parser survey measured what plain
doubles do to larger numbers and priced four responses (suite question 4; survey §5 on #42). For example,
`seed: 12345678901234567890` becomes 12345678901234567168 as a double: two different such numbers then compare equal, sort in
the wrong order, pass the wrong enum check in Ajv, and get the same node version token (§11.3). vmd's own output never contains
such numbers, because int64 and bigint values beyond 2^53 are written as strings, so only foreign files can. Under every option,
an edit never rewrites a number it did not change. Should numbers a double cannot hold be kept exactly, or reported?

## Options

- **(a) Plain doubles, and report what they cannot hold (survey D).** Chosen, as recommended. Values stay ordinary numbers. A
  file with an exact-only number gets the issue `number-not-representable`, an error under the strict default and a warning
  under lenient, with a hint to write the number as a string. Each implementation adds one check and one code, and Ajv, sorting
  and hashing stay standard. A foreign file with such a number fails check until it is changed, the fixture's expected value is
  the nearest double, and a Python implementation, which holds big integers exactly, must round them to match.
- **(b) Keep exactly, mixed shape (survey A).** A double-safe number is a plain number, and an exact-only one becomes an
  `ExactNumber` object holding its decimal text, whose arithmetic throws. All comparisons go through vmd's helpers, Ajv needs an
  adapter, and §11.3 needs a new canonical-JSON rule for such numbers that no library implements, in every language. Code tested
  only with small numbers meets the object for the first time in production. About 4 MB of memory per 300,000 numbers, against
  3 MB for plain doubles.
- **(c) Keep exactly, always an object (survey B).** Every number is an object holding its text, as the `lossless-json` library
  does, so there is one shape and no rarely run branch. Every consumer converts before doing arithmetic, Ajv needs an adapter for
  every number, the same new hashing rule as (b) is needed, and memory is about 20 MB per 300,000 numbers.
- **(d) Doubles plus a hidden side table (survey C).** Cheapest to build. Anything that does not consult the table (Ajv, sorting,
  hashing, `JSON.stringify`) silently uses the rounded value, which is exactly what §4.2 forbids. The survey recommends it in no
  form.

## Decision

(a), with the owner's note that a loss of precision is flagged as an error, at least by default. Values in the value view are
plain doubles. Under every option an edit never rewrites a number it did not change: edits splice only the changed bytes,
because the `yaml` library's writer rewrites numbers, and §13.3 gets that qualifier. The follow-up [F2](F2.md) stated the
resulting rule for numbers, which the log records as the decision.

## Why

The card's reason: it follows the revised survey (#42). The suite's question 4 had recommended keeping every number exactly (b),
but the survey priced both and found that (b) puts the same new rules into every language for data vmd itself never writes; (a)
can move to (b) later without breaking any file. (c) costs an adapter for every number and about 20 MB per 300,000 numbers, and
(d) silently uses the rounded value, which §4.2 forbids. The owner's reason for the error: widening the number type
automatically would assume that every JSON parser vmd and its customers use does the same, so flagging is the safest.

## Owner's note

> If we lose precision when parsing such numbers, we should flag that as validation error, at least by default. Unless we make
> a different decision, to automatically widen number type when parsed, but that would need to assume that all json parsers
> that we use, and customers use will do the same. So flaging as error is the safest.
