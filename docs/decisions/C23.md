## Question

The value view then included each section's computed `$key` (§5.5), which must never be written into a file (§5.4), and the
round-trip guarantee says that parsing what the serializer wrote gives back the same value (§5.8). So the spec had to say what
happens when a value carries a `$key`, and when that `$key` disagrees with the title or anchor (suite question 12). For example,
a program sends `{"$title": "Notes", "$key": "summary"}`; the file gets `## Notes`, which parses back with `$key` `notes`, not
`summary`.

## Options

- **(a) Ignore it, and compare with `$key` recomputed.** Recommended. The serializer drops `$key`, and the guarantee compares
  against the value with its `$key` members recomputed. Programs can pass back a value they read, edited or not. A program that
  changes `$key` hoping to rename a section sees nothing happen, so the documentation points to `$anchor` and `rename` instead.
- **(b) Reject a `$key` that disagrees.** Serializing fails with an error naming the path when `$key` differs from what the title
  or anchor gives. That catches the mistaken rename, but every program that edits a title must also update or delete `$key`.
- **(c) Turn it into an explicit anchor.** A disagreeing `$key` is written as an `<a id="summary">` element. Convenient, but it
  adds anchors to the record behind the writer's back and contradicts §5.4, which says to set a key through `$anchor`.

Chosen: neither. The owner answered Other, with a note proposing escaped identifiers, as SQL tells `rowid` from a quoted
`` `rowid` ``.

## Decision

No option was taken on this card. The session explained that C23 asked something narrower, what the writer does when a program
hands back the computed `$key` it read, and the owner then asked whether a reader has to return `$key` at all. The follow-up
[F9](F9.md), superseding C23, took `$key` out of the value view. The owner's escaped-identifier idea is recorded for VQL (#29),
so that a quoted field name reaches a member literally named like a reserved word or a pseudo-field.

## Why

The card's reason for (a): as the suite recommends; it keeps read, edit and write a straight loop for programs. The owner's
answer addressed a clash of names, which the session said cannot happen on sections, since every name starting with `$` is
reserved there (§5.4).

## Owner's note

> I think there is a way for us to support it, and other languages I think have precedent for it. If I remember correctly a SQL
> dialects may for example have special column like rowid, so if user writes SELECT rowid, they will get the system rowid. But if
> they write SELECT `rowid` they will get the column from the table called rowid (assuming it was permitted). We probably need
> ability to write identifiers in an escaped form in the VQL, and then they will resolve as identifier, instead of the keyword.
> It's not an ideal solution, but pretty much all alternatives as quite bad here.

> then I don't understand C23.  Is the program trying to write a document that has {$key: stuff} where the $key is just a field
> that program is trying to write, and it so happens, that by coincidence we also use $key for something else in our model?
