## Question

The review of Draft v0.1 found that the draft does not fit vampiredb's working dialect: header tables for metadata,
`<a id>` anchors, links relative to the citing file, record ids such as `Minimal_Log` and `0171-long-slug`, and derived link
labels. The review asked: must vmd accept vampiredb's dialect as it is, or would the projects migrate, to front matter for
example? Is rendering on GitHub a hard requirement?

## Options

- **(a) Accept vampiredb's dialect as it is**: vmd parses header tables, the existing anchors and links unchanged.
- **(b) Migrate to vmd's format.** Chosen. Existing conventions (vampiredb's header tables, Belfry's prototype) may change, as
  long as the change is mostly mechanical and the docs and guides are updated with it.

## Decision

(b). The project is greenfield. Existing conventions are not constraints: migration may change them, as long as the change is
mostly mechanical and the docs and guides are updated with it. Belfry is a prototype and not in use; the real tickets are still
in vampiredb's `tickets/`.

## Why

The owner's reasons: Belfry is a prototype, so its dialect is not a requirement, and a migration costs only mechanical changes to
the existing documents and guides. Why the other options lost: Not recorded.
