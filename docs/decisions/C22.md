## Question

A reference has the status `aliased` when it resolves through `.vmd/aliases.jsonl`, which records old paths and anchors after a
rename (§8.5, §13.6). Reference statuses belong to the Validate profile, but aliases were listed under Refactor (§19.2), so an
implementation that supports only Validate could not produce `aliased` (suite question 18, fourth item). For example,
`Minimal_Log.md#room` was renamed to `#room-rule` with `--keep-alias`: an old link to `#room` is `aliased` in a full
implementation and dangling in a Validate-only one. Which profile reads the alias file?

## Options

- **(a) Reading moves to Validate; writing stays in Refactor.** Chosen, as recommended. Every validating implementation reads the
  alias file and reports `aliased`, so check gives the same answer everywhere. Only `rename` and `mv` write the file. Validate
  gains a small JSONL reader.
- **(b) Aliases stay in Refactor.** Validate-only implementations report these links as dangling, so the same store passes check
  in one implementation and fails in another, and reference fixtures need two expected results.

## Decision

(a). Reading the alias file moves to the Validate profile, and writing aliases stays in Refactor. The owner's question whether
aliases are needed at all became the follow-up [F8](F8.md).

## Why

The card's reason: as the suite recommends. The card's consequence for (b), not a reason it gives against it: the same store
passes check in one implementation and fails in another.
