## Question

The owner's [F1](F1.md) note asked for an option that enforces the schema while reading, for cases where correctness matters
more than availability. As drafted, any validation error hid a record from a strict read, including a dangling link caused by
someone deleting a different record, and lint warnings raised to errors. What does the strict read mode refuse? The question came
from the independent review of #50 (Draft v0.4).

## Options

- **(a) Structural errors and schema violations only.** Chosen, as recommended. A strict reader gets only records whose data
  conforms to the schema; a broken link elsewhere or a style warning never hides a record.
- **(b) Every error-severity issue, as drafted.** Strictest, but a record can disappear from strict reads because of a change in
  another record.

## Decision

(a): strict read refuses records with structural errors or schema violations only (§9.5).

## Why

The card's reason: it enforces the schema, as the owner's F1 note says, and nothing else. The card's consequence for (b), not a
reason it gives against it: a record can disappear from strict reads because of a change in another record.

## Applied in

Draft v0.4 (#50, `1043a6c`), §9.5. It narrows the strict read mode of F1's role 4.

Draft v0.17: [AS](AS.md) takes `ref-target-not-allowed` out of §9.5's list of the validation codes that count as schema
violations for the strict mode, a list Draft v0.4 wrote when it applied this decision: whether a strict reader refuses such a
record is the implementation's choice, and vmd returns it. Option (a)'s "A strict reader gets only records whose data conforms to
the schema" therefore no longer holds for `x-vmd-ref`, which amends this decision in the same direction, so AS supersedes it. Its
rule and its reason stand for every other code.
