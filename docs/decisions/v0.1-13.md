## Question

How hard is a git-compatible service that persists to a database, and should vmd offer one? The review weighed three meanings of
"git compatible".

## Options

- **(a) Git-like semantics through vmd's own API**: versions, log, diff, compare-and-swap writes, a local working copy. Moderate.
- **(b) A database-to-git mirror**: one direction is moderate; two-way sync is hard (loops, identity mapping, conflicts).
- **(c) The git wire protocol over a database**: doable with JGit DFS, libgit2 ODB/refdb backends, dulwich or go-git, but a
  read-only clone takes weeks, push with validation more, hardening months. Every record write also rewrites tree objects up to
  the root, and all writers contend on one ref.

The review recommended making the vmd backend contract the interface rather than the git protocol, with a local working copy
(`sync` / `push`) so that agents keep their shell tools. Chosen.

## Decision

The recommendation, (a). Git is a model, not a protocol. A service offering a compatible minimal set of operations is enough.
With a defined CLI and programmatic API, backends and protocols can vary without ties to git.

## Why

The review's reasons: the git protocol costs weeks to months and forces a commit, with tree objects rewritten up to the root, for
every record write, with every writer contending on one ref; a backend contract plus a local working copy keeps agents' shell
tools without implementing packfiles. (b)'s two-way sync is where the pain is.
