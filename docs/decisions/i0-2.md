## Question

`core` must run in Node, on Lambda and in browsers. It cannot see Node's APIs, but TypeScript lets it use browser-only APIs such
as `document` or `localStorage`: code using them compiles, then fails in the CLI or on Lambda. What may `core` assume about its
environment?

## Options

- **(a) Leave it.** The browser APIs stay visible: nothing to set up, but a mistake shows up only if a test happens to exercise
  that code under Node.
- **(b) Only the APIs every runtime has.** Chosen, as the session recommended. Remove the browser library, and declare the small
  set Node, browsers and Deno all provide (`console`, `URL`, `TextEncoder`, `crypto.subtle` and a few others), after WinterTC's
  minimum common web API. A declaration file of about 30 lines to maintain; using `document` in `core` fails the type check.
- **(c) Ban specific globals with a lint rule.** Keep the browser library and list forbidden names: a blocklist, so anything
  nobody thought to list slips through.

## Decision

(b). Only the APIs every target runtime provides (Node, Lambda, browsers, Deno): the browser library is removed from its type
check, and the small set of cross-runtime globals it may use is declared explicitly. Using `document` in `core` then fails the
type check. Consequence for task I1.1: hashing (§11.3) is either asynchronous (`crypto.subtle`) or a small pure-TypeScript
implementation.

## Why

The session's reasons: (b) costs almost nothing and catches the mistake when the code is written, and its list has a standard
behind it; (a) finds a mistake only if a test happens to run that code under Node; (c) is a blocklist, so anything not listed
slips through.
