## Question

Belfry's reasons for leaving git ("every ticket change is a PR", index growth, agents reading whole files) are the limits of
writing to GitHub. Where do tickets live?

## Options

- **(a) A database as the primary store for tickets**, with git as an export or mirror; for docs, git stays primary and vmd is a
  local tool. The session's recommendation in its review.
- **(b) A separate tickets repository in git, with lighter commit rules.** Chosen. Docs stay with the code.

## Decision

(b). Tickets leave the code repository, not git: they should not go through the code's check-in gates or pollute its history. A
separate tickets repository with lighter commit rules is viable. Docs stay with the code.

## Why

The owner's reason: the point of Belfry leaving git was to keep tickets out of the production code's repository, with its check-in
gates and history; documentation, often changed together with code, can stay there. The owner expected the ticket update rate to
suit GitHub, which the session confirmed against GitHub's documented rate limits. Why (a) lost beyond that: Not recorded.

## Owner's note

> For belfry leaving git, the main point is to not have tickets inside the same repo as production code, as it has to go through
> the checkin gates, pollutes the history etc. This is probably ok for documentation, as that is often modified together with
> code. But tickets don't fit there. A separate repo for tickets with lesser commit restrictions seems viable though. The ticket
> update rate, which is not very high, should be ok for github (?).
