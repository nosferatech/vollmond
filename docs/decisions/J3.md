## Question

Item 3 of card J, from the independent review of #58: under [I1.9](I1.9.md), `check` gives `ref-target-unreadable` for a reference
into a record with a structural error, but the `refs` result has no status for it. What does `refs` report?

## Options

- **(a) A new status, `unreadable`. A reference with no fragment, such as `../data/broken.json`, is still `ok`, since it needs
  only the file to exist.** Chosen, as recommended.

Other options: Not recorded.

## Decision

Card J's option (a), accepting every recommendation. `refs` gets the status `unreadable` for a reference with a fragment into a
record that has a structural error, which `check` still reports as `ref-target-unreadable`. A reference with no fragment to such a
record is `ok`. This closes §20's open question 7 and the I1.9 reading (§8.5, §14.2, §20, Appendix D, suite README). "No fragment"
covers `#` alone, which §7.1 makes the root too. Three points are the agent's reading, as the log records: the `ok` reference's
target is the record's root, `{"path": ..., "at": "", "address": ""}`, as for any record; it raises no warning; and `resolve` of
the same root address still fails, which is intended, since a reference's status says only that its target exists, while a
resolve returns its value.

## Why

The card's reason for the reference with no fragment: it needs only the file to exist. For the whole card: each recommendation
"keeps one rule per thing and matches what the libraries vmd builds on can check".

Why the other options lost: Not recorded.
