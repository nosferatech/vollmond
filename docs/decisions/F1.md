## Question

On [C2](C2.md) the owner chose strictness: an error fails parse, and parse still reports every error it finds. The session agreed
for malformed records, but asked which errors count. A schema violation (`status: Opne`) or a broken link is not malformed data,
and under a literal reading of C2 it would make the whole ticket unreadable, drop it from queries, and leave agents only `cat` to
see it. [C15](C15.md) adds a case: in the strictest mode an unsupported tag in a heading is an error, so one `<kbd>` would make a
whole design document unreadable. Either way, writes are rejected and CI fails, so bad data does not spread; the difference is
only what a reader sees in the meantime. Which errors make a record unreadable?

## Options

- **(a) Structural errors fail parse; validation errors leave it readable.** Chosen, as recommended. Syntax errors, values
  outside the data model, misplaced data blocks, bad `$` members, malformed `$ref` objects and numbers a double cannot hold fail
  parse. Schema violations, dangling references and strict-mode escalations attach to a readable record, fail check (exit 4) and
  are refused by gate-mode writes. `vmd query` and `ls` say how many records could not be read, so none vanish silently.
- **(b) Every error-severity issue fails parse.** One rule. A typo in an enum value or a renamed anchor elsewhere makes the record
  unreadable until fixed; queries list it only as unreadable. Strict mode turns warnings into errors, so it also turns them into
  unreadable records.

## Decision

(a). Structural errors fail parse: syntax errors, values outside the data model, misplaced data blocks, `$` members where none
are allowed, malformed `$ref` objects, and numbers a double cannot hold. Validation errors (schema violations, dangling
references, escalated warnings) attach to a readable record, fail `check` with exit code 4 and are refused by gate-mode writes.
`vmd query` and `ls` report how many records they could not read. Parse and check report every error they find, not only the
first. The owner's note on the roles of readers, validators, backends and queries is recorded as [F1a](F1a.md).

## Why

The card's reason: it keeps the owner's strictness where data is malformed, while a record that is well-formed but wrong stays
visible, so that it can be found and fixed with vmd itself. The log's: F1 narrowed C2 "so that a well-formed but wrong record
stays visible and can be found and fixed with vmd itself". (b) makes a typo or a renamed anchor elsewhere hide a record, and
turns strict-mode warnings into unreadable records.

## Owner's note

> All right, I think there is a subtle distinction here. That is probably worth elaborating in the design:
> 1) A reader opened on not validated, should read the data as long as it's syntax is proper.
> 2) A validator should report all error (syntax, schema, constraint violations), and fail to validate according to the
> configured strictness.
> 3) A backend should reject any update that does not validate.
>
> This then brings the question: When running a query, what should happen if the data does not pass validation:
> a) if query is running on not validated data (e.g. a local edit copy), then query should work as a best-effort.
> b) if a query is running on validated data (or data that was supposed to be validated). This is less obvious. Because if user
> correctness depends on schema conformance, and data doesn't conform in practice, then it could cause serious problem? But the
> premise here is that the backend somehow contains data that fails to validate against its constraints, so at this point
> nothing we will do will be correct.  There is I think one more scenario. A backend data is correct, but whoever is reading is
> misinterpreting it? If I was running a reader that was using an incompatible format version compared to the backend, I'd
> probably like that reader to fail very loud, so that I can fix it, at lest in tests and staging environments.  On the other
> hand when I was running this in production, it may depend on whether I want correctness at a cost of availability or the other
> way around.
> So I think, me may actually need to offer an option, to strictly enforce schema while reading, for cases where correctness is
> more important than availability. As a default I think we can let readers read to their best effort, and assume that backend
> is actually correct.
> This question I think it quite important, and we may need to discuss it later. The case of mismatched readers/writers is scary,
> and I think it will require a good systematic solution.
