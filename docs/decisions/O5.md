## Question

Unicode 18.0 adds combining marks that Unicode 17 does not know. A runtime with Unicode 18 normalizes `a`, U+1ADE, U+0323 to `ạ`
and U+1ADE, while a Unicode 17 runtime leaves it alone, so the same heading could get different anchors depending on the Node
version. What does the slug rule do with code points the pinned Unicode version does not assign?

## Options

- **(a) Step 2 of the slug rule also removes code points that are unassigned in the pinned Unicode version before normalizing**,
  so every runtime at 17 or later gives the same anchor. Chosen, as recommended.
- **(b) Keep step 2 as it is.** The same heading could get different anchors on Unicode 17 and Unicode 18 runtimes.

## Decision

(a), with card O's option (a), accepting every recommendation. Step 2 of the slug rule also removes the code points that are
unassigned in the pinned Unicode version, 17.0.0, before NFC, so that every runtime at 17 or later derives the same anchor (§6.3),
with a case. The card's example was checked against the final data of both versions: U+1ADE is unassigned in 17.0.0 and is
COMBINING GRAVE-DOT, combining class 230, in 18.0.0, so `a`, U+1ADE, U+0323 normalizes to U+1EA1, U+1ADE on an 18 runtime and
stays as written on 17. Unassigned means `Cn`, noncharacters included, with a second case on U+FDD0. This changes the slug rule
of [H5.2](H5.2.md), which §6.3 allows only with a new version of the specification; Draft v0.10 is that version. No warning
period or migration is needed, since nothing derived anchors yet: the slug is implemented in task I1.5. §6.3 also says when
`unicode-runtime-older` is raised.

## Why

The card's reason: it keeps anchors stable across Node versions, which (b) does not. For the card as a whole: each rule makes the
CLI predictable for agents and keeps anchors stable across Node versions.

## Applied in

Draft v0.10 (#78, `d1e0a60`), §6.3; the slug, in task I1.5 (#82, `4614512`), follows it.
