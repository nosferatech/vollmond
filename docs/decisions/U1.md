## Question

Which validator does core use for JSON Schema 2020-12? The plan's §1.2 and the draft's Appendix C named Ajv with `ajv-formats`.
The design of phase I2 measured the candidates on 2026-10-11, and its independent review corrected the first version's evidence
against Ajv, so the question was restated narrowly:

- Ajv 8.20.0 with `ownProperties: true` gets `required` and `properties` with names like `toString` right, but still drops a
  `properties` entry named `__proto__`: `{"__proto__": 5}` passes `properties: {__proto__: {type: string}}`.
- On the JSON Schema suite's `unevaluated*` cases, Ajv gives 13 wrong verdicts of 199 tests in the design's probe; Bowtie's
  published 2020-12 run also shows 15 wrong verdicts on `$dynamicRef` and `$dynamicAnchor` and 6 on `unevaluated*`. vmd cannot
  correct those.
- `@hyperjump/json-schema` 1.18.0 gave no wrong verdict in the probes or in Bowtie's data, and its error locations are exact. Its
  costs: some APIs it relies on are marked experimental, and its schema registry and format settings are process-wide.

## Options

- **(a) `@hyperjump/json-schema` 1.18.0.** Chosen, as recommended. No known wrong verdicts. Appendix C and the plan name it in
  place of Ajv and `ajv-formats`. Core depends on hyperjump and its peer; the experimental APIs are pinned exactly, and the
  process-wide state is handled by digest-keyed schema URIs and a bounded memo of 64 schema sets (design §3.1.1). It generates no
  code, brings no messages, so vmd writes its own, and has 7 dependencies with its peer.
- **(b) Ajv 8.20.0 with workarounds.** `ownProperties: true`, core checking a `properties` entry named `__proto__` itself,
  `$dynamicRef` refused as `schema-invalid`, and the `unevaluated*` failures listed as known deviations. The design measured it
  as the fastest by a factor of four to six (6 ms for 1,000 validations of a 200-member record, against 25 to 36 ms), synchronous,
  with state per instance and exact locations; it generates code with `new Function`. Under (b) the design keeps its shape and
  loses its section 3.1.1.
- **(c) json-schema-library 11.6.5.** Clean on Bowtie's run, but its error locations do not escape `/` and `~`, so `#/a/b` is
  ambiguous for a member named `a/b`, which needs a workaround; one of its six dependencies is `valid-url` 1.0.9 of 2013.
- **(d) `ata-validator`.** No wrong verdict and no error on Bowtie's run, as 1.46.0, and pure JavaScript, but its first release
  was on 2026-03-21, with 159 versions published, six of them in the five days before the design. Not probed; the fallback if
  hyperjump disappoints in I2.2.
- **(e) `@cfworker/json-schema` 4.1.1.** Looked at by the design: it reports every declared property of a null-prototype object
  as an additional one, so it is out.

## Decision

(a): core validates schemas with `@hyperjump/json-schema` 1.18.0, pinned exactly, and Appendix C and the plan name it in place of
Ajv and `ajv-formats`.

## Why

The card's reason: "Narrowly: it is the one without wrong verdicts. Ajv's are in features vmd can't patch around. Against it:
experimental APIs and global state, both contained." The design's: what decides it is the 21 wrong verdicts on `unevaluated*` and
`$dynamicRef`, in keywords a schema author uses without knowing which validator runs. Ajv's `__proto__` skip could be worked
around (b), its wrong verdicts could not; the design weighed Ajv's speed, synchronous API and per-instance state against that, and
said that if the owner weighed process-wide state above the `unevaluated*` verdicts, (b) would be the alternative. Code
generation mattered less than the first version of the design said, since I7's pages run VQL, not validation. (c) needs a
workaround for its locations. (d) is too young: a dependency of core is read by every implementation's maintainers for years,
and its rate of change is a risk the probes cannot measure. (e) gets null-prototype objects wrong.
