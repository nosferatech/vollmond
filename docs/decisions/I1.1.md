## Question

Item 1 of card I1, from #57's open questions (#53 question 2): for a block anchor such as `- <a id="room"></a>**Room.** …`, does
the range include the list marker, nested content, the trailing line break? And where does an issue on a block anchor go?

## Options

- **(a) Leave the ranges to the Markdown parser task (I1.4)**, as [C11](C11.md) did for spans. Chosen, as recommended. The two
  cases stay pending until then. An issue on a block anchor goes at the `$body` holding it, as Appendix D already says.
- **(b) Specify the ranges now: the CommonMark block's own span.** #53's recommendation for its question 2: "a list item from its
  marker to the end of its last line, a paragraph from its first to its last character, with no trailing line break", with `at`
  the `$body` that holds it, as for prose references. [K1](K1.md) later adopted ranges of this kind.

## Decision

Card I1's option (a), accepting every recommendation: block anchor ranges are specified with the Markdown parser (task I1.4), as
C11 left source-map spans to it. The two block-anchor cases stay `pending`, so #7 stays open. An issue on a block anchor is
attached to the `$body` that holds it (§6.2, Appendix D).

## Why

The card's reason for the whole card: each recommendation "keeps vmd strict without rejecting data that is plainly fine". For this
item, the card points to C11's precedent of leaving spans to the Markdown task.

Why (b) lost: Not recorded.

## Applied in

Draft v0.6 (#58, `c3879b7`), §6.2 and Appendix D. [K1](K1.md) settled the ranges in Draft v0.7, and the two cases lost
`pending`.
