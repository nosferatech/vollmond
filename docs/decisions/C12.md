## Question

A heading's derived anchor was to be the id GitHub gives it, so that a link such as `file.md#what-is-confirmed` works both on
GitHub and in vmd (§6.3). The capture of #37 rendered 693 headings through GitHub and found §6.3's one-sentence rule wrong or
silent in eight places, and proposed wording that matches all 673 permalinks GitHub emitted (slug report; suite question 11).
GitHub slugs the text a reader sees, keeps letters and marks beyond A to Z, turns only the ordinary space into a hyphen, does no
Unicode normalization, numbers repeats by skipping ids already taken, and counts headings inside block quotes and list items and
raw `h2` elements, although vmd does not treat them as sections. Should derived anchors copy GitHub's heading slug rule exactly?

## Options

- **(a) Adopt GitHub's rule in full (the report's wording).** Recommended. vmd computes anchors from the rendered text, with the
  proposed character classes, case mapping pinned to a Unicode version by the suite, the skip-taken repeat rule, and container
  headings counted. Every link that works on GitHub resolves in vmd. `github-slugger` alone is not enough, since it takes plain
  text and its edge cases are unverified, so core extracts the rendered text from the Markdown tree. A change on GitHub's side
  shows up as failing fixtures.
- **(b) A simpler rule of vmd's own.** Chosen. For example, slug the `$title` source with ASCII-style letters and a plain `-1`,
  `-2` count. Much less code, but 64 of 658 headings in the capture get a different anchor from GitHub's, mostly headings with
  links, images, entities or HTML. Links written against GitHub break in vmd for those headings, and `vmd check` reports them as
  dangling.

## Decision

(b): the rule is vmd's own, and vmd does not follow GitHub's changes. The follow-up [F5](F5.md) chose that rule on its merits.

## Why

The owner's reason: if GitHub changes, vmd should not be required to change; any use of a derived slug in an anchor is asking for
trouble once the rules change, so the chance of a non-backward-compatible change must be minimal, with warnings and validation
before a change is enacted, and chasing GitHub runs contrary to that. The card recommended (a) because vmd followed GitHub by
stated principle and the cost is code in core, not effort for authors. The session then objected that the "simpler" rule leaves
about 10 percent of captured headings with a different anchor and gives an ASCII-only rule no anchor for Japanese or Greek
headings, which led to F5.

## Owner's note

> I'm not excluding github rule, but if github changes, we should not be required to change. Which is why I'm suggesting rule on
> our own. I think we need to be very careful what we promise wrt derived slugs. And we probably can't promise that we will never
> change the slug derivation rules.  Basically any use of derived slug in an anchor is essentially asking for trouble. As soon as
> rules change, that anchor may break or point to a wrong place. So for safety, I think we want to make it so that the chance that
> we will need to change it in a non backcompat way is minimal. And then hopefully issue warnings and ways of validating before
> the change actually is enacted.
> Chasing github would go contrary to that.
