## Question

A heading made only of punctuation, an emoji or an image has an empty slug. GitHub still counts it when numbering repeats, gives
the first such heading the id `""` (a link to plain `#`) and later ones `-1`, `-2`, and sometimes emits no permalink at all, for
reasons the capture could not explain (slug report, item 8). For example, three headings `## ...`, `## 🚀` and `## Tail` get the
GitHub ids `""`, `-1` and `tail`. Under either option such a section's key (§5.5) is the empty string, so two of them in one
record are duplicates under strict mode unless one has an explicit anchor. Does a heading whose slug is empty get a derived
anchor?

## Options

- **(a) No derived anchor, but still counted.** Chosen, as recommended. Such a heading has no derived anchor, so `file.md#-1`
  resolves to nothing in vmd. It still uses up `""` and `-1` in the numbering, so every later heading gets the same anchor as on
  GitHub. Authors who want to link to it add an explicit anchor.
- **(b) Its anchor is GitHub's id.** The anchors are `""`, `-1`, `-2` as GitHub emits for most such headings, so a link to `#-1`
  resolves. The first one cannot be addressed at all, because `file.md#` already means the record's root, and fixtures cannot be
  checked reliably against GitHub, which drops some of these permalinks.

## Decision

(a). A heading whose slug is empty has no derived anchor, but its candidate still counts as used.

## Why

The card's reason: the slug report's proposed wording; GitHub's own behavior here is irregular and the links it produces are not
usable, while the numbering, which affects every later heading, still matches. (b) leaves the first such heading unaddressable
and its fixtures uncheckable.
