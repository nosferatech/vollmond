## Question

CI jobs on GitHub are expensive, and validating on GitHub is slow when it waits for an Actions runner. Are there lighter
alternatives, such as calling an external service (an AWS Lambda) when a merge is about to happen, to validate and update the
index after the commit?

## Options

The session's three patterns, each a GitHub App driven by webhooks and backed by Lambda:

- **(a) Pattern A: check after the commit.** Chosen for the tickets store. A push webhook triggers a Lambda that re-validates the
  changed records and those that reference them, publishes the index and posts a commit status. Invalid data can land, but it is
  visible.
- **(b) Pattern B: a required check on pull requests and merge groups**, with no Actions involved. For stores that already work
  through pull requests and the merge queue.
- **(c) Pattern C: a gatekeeper branch** that only the app may update; clients push to `incoming/<name>`. The nearest thing to a
  pre-receive hook, at the cost of more moving parts.
- **(d) A warm self-hosted Actions runner on AWS.** It saves the start-up wait, but costs an instance that is always on and is
  still a runner; the session did not recommend it.

## Decision

A GitHub App driven by webhooks validates in Lambda: pattern A (check after commit, posting a commit status), B (a required check
on pull requests and merge groups), or C (a gatekeeper branch that only the app may update). Pre-receive hooks are not available on
github.com. The tickets store uses pattern A.

## Why

The session's recommendation: start the tickets repository with pattern A plus `vmd check` before pushing, move to C if invalid
pushes become a problem, and use B for any store that already works through pull requests. Each pattern takes seconds and needs no
runner. github.com cannot reject a push synchronously, since pre-receive hooks exist only on GitHub Enterprise Server.
