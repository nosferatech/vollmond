## Question

The decision log said tags select sets of nodes through VQL (`@tags:decision`) or through references that the schema declares as
having many targets, and §7.4 counts a tag as a selector. But the address grammar of §7.1 had no way to write a tag, so a
many-reference could not name one (suite question 18, third item). For example, a design document wants a field that references
every section tagged `decision` in `tickets/0171-x.md`.

## Options

- **(a) A first step written `.tag`.** Recommended. `tickets/0171-x.md#.decision` selects every node tagged `decision`, following
  HTML's `.class` selector, which §6.1 already cites as the model. A dot names a tag only in the first step, so a root field whose
  name starts with a dot must then be reached by an exact path. On GitHub such a link goes to the top of the page, since no
  element has that id, which is acceptable for a set.
- **(b) A VQL term in the fragment.** `tickets/0171-x.md#@tags:decision` reuses the VQL pseudo-field syntax, so agents learn one
  form. Longer to write, and it invites further VQL inside fragments, which the grammar then has to fence off.
- **(c) Only VQL selects by tag.** No grammar change. References cannot select by tag, so §6.4 and §9.3 drop that case and a
  many-reference lists its targets one by one. This reverses part of the logged decision on tags.

Chosen: neither. The owner answered Other: complex selectors need a more elaborate syntax, and that is a long discussion.

## Decision

No option was taken on this card. The follow-up [F7](F7.md) deferred tag selection to a selector-language design issue.

## Why

The card's reason for (a): the suite offered adding syntax or restricting tags to VQL without choosing, and (a) keeps the logged
decision with the smallest grammar change, mirroring HTML as §6.1 does; choose (c) if no customer needs tag references before
I2. The owner's reason for answering Other: users may want and, or and not conditions, and selectors need to distinguish
filtering from projection with descent, and possibly a final projection.

## Owner's note

> For complex selectors, I think we will need a more elaborate syntax, because users may want to specify and / or / not
> conditions. And similarly we will need ability to distinguish the filtering vs projection+descent, and possibly a final
> projection as well.
> I'd expect this to be a very long discussion.
