## Question

Item 4 of card I1, from #57's open questions: [H3.13](H3.13.md) covers a byte order mark in Markdown only. What happens to a BOM
in a JSON or YAML record, and do its bytes count in source-map offsets?

## Options

- **(a) Skipped, as in Markdown (H3.13).** Chosen, as recommended. Offsets still count from the first byte of the file, the BOM
  included, since offsets are file bytes ([C10](C10.md)).

Other options: Not recorded.

## Decision

Card I1's option (a), accepting every recommendation, read with the owner's note on #54, given before the card was answered. A
BOM in a JSON or YAML record is skipped, as in Markdown, and offsets count from the file's first byte, the BOM included (C10).
Only a BOM at byte 0 is one, in every format; a U+FEFF elsewhere is an ordinary character, Default_Ignorable and so dropped from
slugs, and in Markdown it does not restart front matter detection (§5.1, §5.3, §5.9).

## Why

The card's reason: one treatment in every format, with offsets as file bytes (C10). The owner's note settles where a BOM may be:
"there should only be one at the beginning of the file, and it should apply to the entire file". For the whole card: each
recommendation "keeps vmd strict without rejecting data that is plainly fine".

Why the other options lost: Not recorded.

## Applied in

Draft v0.6 (#58, `c3879b7`), §5.1, §5.3 and §5.9. [J4](J4.md) made a U+FEFF where YAML does not allow one a `syntax-error`, and
[J5](J5.md) settled columns, writes and the files the rule covers.

[J4](J4.md) reverses it in part: a U+FEFF in YAML away from byte 0 is a `syntax-error`, not an ordinary character.
