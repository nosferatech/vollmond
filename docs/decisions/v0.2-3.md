## Question

Draft v0.2 gave every node a byte-range span, which implies a flat serialized source always exists. The owner asked how important
the byte range is, since a path already identifies every node. Are spans part of the data model?

## Options

- **(a) Spans in the data model**, as Draft v0.2 had them: every node has a byte range, so a flat source must always exist.
- **(b) Spans leave the model, as an optional source map from file-based parsers.** Chosen, as the session proposed.

## Decision

(b). A node's identity is its path. Source locations are an optional source map produced by file-based parsers, used for
span-preserving edits, error locations, and the `--source` view. A reference inside prose is located by (node path, offset within
`$body`). Byte and line ranges remain in the storage contract.

## Why

The owner's reason: a path always identifies a node, so spans add nothing to identity, and their uses (reading a range directly
from the source, finding the smallest span containing others) are optional. The session added that the library still needs a
source map for span-preserving edits, `line:col` in errors and references inside prose, and that a database backend can locate a
reference by node path and offset. (a) would require a flat serialized source for every backend.

## Owner's note

> 3) 5.1 Overview. Span is interesting: I agree a byte range is convenient, however this implies that there always must exist a
> flat serialized source. We can probably start with this. How important byte range is? In the proposed object model, we already
> assume that everyone has a "key" that identifies it in the parent node (with exception or document root). Meaning that a path
> can always identify the node, so if access by span or path were equally good, that would limit the need to rely on span. The
> span is helpful when trying to read a range directly from the source, or to find minimum span that contains N other spans,
> etc. But those seem like optional nice to haves, rather than hard requirement.
