## Question

Question 1 of the phase I1 design (#59), item 1 of card K. [C11](C11.md) left spans, the bytes a node's range covers, to the
Markdown task, and [I1.1](I1.1.md) did the same for block anchor ranges. Approve the ranges of the design's section 3.6 now, or
leave them to the Markdown pull request?

## Options

- **(a) Approve the design's section 3.6 now.** Chosen, as recommended. A member has a `range` for its value and a `memberRange`
  from key through value, used for delete; a section has one range for both set and delete. A small spec pull request writes
  them into §5.9 and §6.2 before the Markdown work starts.
- **(b) Leave them to the Markdown pull request, as C11 and decision I1.1 do.**

## Decision

(a), through card K's option (b), which accepted every recommendation but question 3's. The spans of the design's section
3.6 go into §5.9 and §6.2. A section's range, from its heading line to the next heading or the end of the file with its trailing
blank lines, serves `get`, `set` and `delete`, so sections tile the file. An object member has a `range`, its value, which `set`
replaces, and a `memberRange`, from its key to its value, which `delete` removes (§5.10's `@source`). A block anchor's range is
its CommonMark block in the `$body` without the trailing line break. This settles the block-anchor ranges that C11 and I1.1 had
left to task I1.4: the two suite cases that waited on them lose `pending`, and #7 closes.

## Why

The design's reason: approving them now lets the Markdown work start from a rule. For sections and members, the design's first
draft in #59 gave the reasons of the chosen ranges: removing a section then leaves no stray blank lines, and an exact path names
the value that `set` replaces. The card's reason for the whole card: "The reviewer checked each recommendation and called them
sound."

Why the other options lost: Not recorded.
