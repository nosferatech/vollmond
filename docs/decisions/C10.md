## Question

Several places give a position: a block anchor (§6.2) resolves to a range of its section's `$body`, a link inside prose is
located by an offset into `$body` (§5.9, §14.2), and an error message gives `line:col` (§12.3). The spec never said the unit,
and with non-ASCII text the common units disagree (suite question 6). For example, in the body text `Größe 🌕 [x](a.md)` the
link starts at UTF-8 byte 13, UTF-16 code unit 9, or code point 8. Which unit do offsets and columns use?

## Options

- **(a) UTF-8 bytes for offsets; lines from 1, columns in code points.** Chosen, as recommended. Offsets match the byte ranges of
  source maps and of the read operation (§11.2), so a program can cut the file or the body bytes directly. JavaScript has to
  convert, since its strings count UTF-16 units. Error positions read the way people count characters, except for emoji built
  from several code points.
- **(b) UTF-16 code units throughout.** This is what JavaScript and the Language Server Protocol use by default, so core converts
  nothing. Python and Rust implementations must convert, and offsets no longer line up with §11.2's byte ranges.
- **(c) Code points throughout.** Neutral across languages and intuitive, but neither JavaScript strings nor byte-oriented
  storage index by code point, so every implementation converts, and cutting a file at an offset needs a scan from the start.

## Decision

(a). Offsets are UTF-8 bytes, lines count from 1, and columns count code points. Clients that need other units convert.

## Why

The card's reason: as the suite recommends, for consistency with the byte ranges the storage contract already uses. The owner's
reason: offsets asked of a backend are in the backend's encoding, no backend will want to convert between UTF-8 and UTF-16 to
accept different client offsets, and clients do not want to know which encoding a backend chose, so assume UTF-8. (b) and (c)
misalign offsets with §11.2's byte ranges or make every implementation convert.

## Owner's note

> In this case, I think it depends what the encoding is used to store the data, and when asking for specific offets, it's going
> to be a backend encoding, and I'm going to guess no backend will want to do conversions from UTF8 to UTF16 and other way around
> just to accept different client offsets.  But, clients don't want to deal with having to know what encoding backend decided
> on. So lets just assume UTF-8. Any javascript  client that wants to deal with unicode offsets of a string, would need to convert
> (which presumably it will need anywas to satisfy the file formats or network protocol)
