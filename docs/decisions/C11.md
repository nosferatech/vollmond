## Question

A source map gives each node's byte range in its file (§5.9). Fixtures for it need to know exactly which bytes each node covers,
and the Read profile (§19.2) must say whether an implementation without files needs one at all; §5.9 called source maps optional,
while §19.1 listed them in the suite (suite question 5). For example, does the section `## Notes` run from its heading line to
the next heading, with or without the blank lines before that heading? Is the front-matter field `status: Open` the bytes
`Open`, or the whole line? When are source map spans fixed, and does reading require them?

## Options

- **(a) Spans decided by the Markdown parser task; optional for Read.** Chosen, as recommended. The Markdown parser task (I1.4,
  #13) proposes the spans from what the parser reports and what span-preserving edits need, and `source_map` fixtures are written
  then. The Read profile lists source maps as an option an implementation declares, since a database backend has no files. #6
  goes ahead now without `source_map` cases.
- **(b) Decide the spans now, in #6.** Fixtures are complete sooner, but boundaries chosen before the parser and the editor exist
  are likely to change when edits (I4) need different ones, so the fixtures churn.
- **(c) Required for the Read profile.** Every reader must produce source maps, which shuts backends without files out of the
  Read profile even though they can serve values, outlines and `get`.

## Decision

(a), with the owner's note. Spans are decided by the Markdown parser task (I1.4), and source maps are optional for the Read
profile. A node's span covers exactly the UTF-8 bytes that `get` returns for it.

## Why

The card's reason: as the suite recommends; the people who build the parser and the editor are the ones who can say which
boundaries edits need. The card's consequences for the other options, not reasons it gives against them: (b) risks fixtures that
churn when edits need other boundaries; (c) shuts backends without files out of the Read profile.

## Owner's note

> But I'd imagine the span should match what client gets when fetching a node by it's key in UTF-8.
