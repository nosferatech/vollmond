## Question

§9.3 says that a semantic path step matches a single key member, but does not say whether a list can have several.

## Options

- **(a) One string key member per list.** Chosen, as recommended. Several are `schema-invalid`. An item without a key, or with a
  key that is not a string, is a `schema-violation` at the item, reachable only by its `$anchor` or its exact path, since no step
  indexes a keyed list (§7.3).
- **(b) Composite keys now.** Needs a rule for which member a step matches, which §9.3 leaves open.

## Decision

(a). §5.6 and §9.3 state it.

That this narrows [v0.2-9](v0.2-9.md), whose keyed lists allowed composite keys, and so supersedes it, is this record's
reading; the card does not say so.

## Why

The card's reason: "No case needs composite keys; allowing them later is an addition under U21." The design adds that allowing
several key members later relaxes a `schema-invalid`, an addition under [U21](U21.md) once [U12](U12.md) makes an invalid schema
fail every read. The card's consequence for (b), not a reason it gives against it: it needs a rule for which member a step
matches.
