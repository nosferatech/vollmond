## Question

Role 3 of the owner's [F1](F1.md) note says a backend rejects any update that does not validate. But §11.1 makes backends plain
storage that knows nothing about schemas, and §9.4 allows client and after-commit validation, where invalid data can be stored
(pattern A on GitHub, for one). The draft read it as: a backend that validates (gate mode) rejects. Role 4, that queries assume
the backend is correct, then has a basis only in gate mode. Does "a backend rejects invalid updates" hold everywhere, or in gate
mode? The question came from the independent review of #50 (Draft v0.4).

## Options

- **(a) Gate mode only, said outright.** Chosen, as recommended. The guarantee holds where a gate validates (a service backend,
  pattern B or C on GitHub). Elsewhere, data may be invalid, `check` reports it, and the strict read mode is the remedy for
  readers that need correctness. Plain filesystems and git keep working with plain tools.
- **(b) Every backend must validate.** Every backend needs vmd's library and the schemas; a plain git push or a plain filesystem
  write could never be a vmd store, which contradicts goal 8 (plain tools stay first-class).

## Decision

(a), with the owner's definition of a backend: everything that runs regardless of the client, that is storage, server-side
scripts, commit protocols, merge queues, CI runners and Lambda calls. Client-side hooks and scripts are not the backend. A backend
that validates before accepting a write (gate mode) is a validating backend. GitHub plus a Lambda function that validates after
the commit (pattern A) is a weakly validating backend, whose constraints hold except for the latest commits still being
validated, and a client that syncs only to commits marked green sees a validating backend. The role of queries, which assume the
backend is correct, rests on this (§9.4, §9.5, §11.1).

## Why

The card's reason for (a): it keeps plain tools and simple setups possible, as the owner asked earlier, while being explicit
about where the guarantee holds. (b) would make a plain git push or filesystem write unable to be a vmd store, against goal 8.
The owner's note drew the line between what is and is not a backend: hooks and scripts on the client are not, and "Anything
that is initiated regardless of client is effectively a backend".

## Owner's note

> This brings an interesting distinction what is backed and what is not. So how about:
> - hooks and scripts running on the client, as not backend.
> - storage and server side scripts, commit protocols, merge queues, runners, lambda calls. Anything that is initiated regardless
> of client is effectively a backend. So a github + aws lambda that validates would be considered a validating backend. If
> lambdas run post commit, that makes the backend validation async, so it is kinda weakly validating backend (it generally
> promises contraints hold, except a latest commit(s) that still are going through validation. But if client was only syncing
> to commits that were marked green, then it would also be considered a validating backend.
