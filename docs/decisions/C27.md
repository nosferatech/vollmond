## Question

The suite's version follows the spec's (suite README, Versioning). The draft changed under one number as decisions were applied,
and Draft v0.3 took several rounds, so a suite release that says it implements v0.3 does not name one set of rules (suite
question 19). For example, two copies of the proposal can both say Draft v0.3 and disagree on the trailing-hyphen rule of
[C13](C13.md). How does the spec's version number change as decisions land?

## Options

- **(a) Raise the minor version each round.** Chosen, as recommended. Each round of decisions applied to the spec raises it (v0.4,
  v0.5, and so on), and the decision log names the round. Every suite release names one exact state of the rules. Version numbers
  move quickly during I0, which is harmless before 1.0.
- **(b) Keep the number, add a date or commit.** Fewer version bumps, but the suite must cite a commit id, which is harder to
  compare and to talk about, and two releases of the suite can claim the same version.

## Decision

(a). The spec's minor version rises with each decision round. This round gave Draft v0.4.

## Why

The card's reason: as the suite recommends. (b) makes the suite cite commit ids and lets two releases claim one version.

## Applied in

Draft v0.4 (#50, `1043a6c`), the status line; every later round raised the minor version.
