## Question

Draft v0.1 used `## Title {#id}` anchors and `[[record#id]]` wikilinks, which GitHub shows as literal text, so its "Level 0:
readable by any tool" broke on the main human viewing path. The review suggested separating the model (tree, addresses,
references, schemas) from the syntax, and choosing for each format the syntax that is already idiomatic there: standard
Markdown links, explicit `<a id>` anchors or heading slugs, `$ref` in JSON and YAML. Which syntax do record ids, references and
section ids use?

## Options

- **(a) The syntax that is already idiomatic in each format.** Chosen, as the review suggested. Standard Markdown links relative
  to the citing file are the default reference form, so rewriting means rewriting relative paths, not store-root addresses.
- **(b) Draft v0.1's own syntax**, `{#id}` and `[[wikilinks]]`, which GitHub renders as literal text.

The review's first version also proposed pluggable dialects per store (metadata carriers, id sources, reference syntaxes,
including header tables and wikilinks).

## Decision

(a). Record ids, references and section ids must fit both GitHub and the filesystem. Each should be idiomatic in the format it is
embedded in, and standard renderers should do a reasonable job. `<a id>` anchors are an acceptable compromise. Relative paths
must be supported, which needs care for purely programmatic access. Where a format has no idiom, adopt a convention with
precedent, such as `$id` and `$ref` in JSON and YAML.

## Why

The review's reason: GitHub does not render `{#id}` or wikilinks, and standard Markdown links render everywhere and agents write
them unprompted. Why pluggable dialects lost: Not recorded.
