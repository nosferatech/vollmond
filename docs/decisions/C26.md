## Question

§3.2 forbids paths that cannot be checked out everywhere, such as two names differing only by case, Windows reserved names like
`CON.md`, and very long paths. A fixture for those rules would itself break the checkout on macOS or Windows; Windows limits paths
to 260 characters unless long paths are enabled, which is less than §3.2's 1024 bytes once the checkout directory is added (suite
question 16). For example, a fixture store holding both `Notes.md` and `notes.md` is a single file on a Mac. How are path rules
tested that cannot exist as files?

## Options

- **(a) Leave them out for now.** Chosen, as recommended. I0 has no cases for these rules. Later the case format adds a manifest
  store, a JSON file mapping store paths to contents, which the runner gives its implementation through an in-memory backend, only
  for such cases. The rules stay untested until then.
- **(b) Add the manifest store now.** The case format gains a second kind of input in I0, and every runner must support an
  in-memory backend from the start, before any other case needs one.
- **(c) Write the files at test time.** The runner creates them in a temporary directory. That fails on the very file systems the
  rules protect, so results depend on the machine the suite runs on.

## Decision

(a). Paths that cannot be files are left out of the suite for now.

## Why

The card's reason: as the suite recommends; nothing in I0 or I1 depends on these rules being tested. (b) makes every runner
support an in-memory backend before any other case needs one; (c) gives results that depend on the machine.
