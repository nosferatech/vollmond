## Question

The owner's answers to [C4](C4.md), [C5](C5.md) and [C6](C6.md) combine into one rule, which the session stated for
confirmation: a number means its nearest double; it is an error when its value is an integer and the double differs from it
(`9007199254740993`), when it overflows (`1e400`), or when a non-zero value underflows to zero (`1e-400`); a fractional number
with more digits than a double holds is accepted and means its nearest double, so `0.10000000000000001` equals `0.1` without an
issue. On the owner's C5 question, the session answered from memory that most current serializers print the shortest form that
round-trips (JavaScript, Python since 3.1, Go, Rust, .NET Core 3 and later, Java since 19), with `printf %.17g` and Java before 19
the exceptions, and that no respectable serializer emits `1e400` from a double. Under F1 (a), the error is structural.

## Options

- **(a) Confirm: nearest double, with the three errors.** Chosen, as recommended. Implementations need one check: is the value an
  integer the double does not hold, an overflow, or an underflow of a non-zero value. Fixtures expect `0.10000000000000001` to
  read as `0.1`. §4.2's sentence that a number means its decimal value changes to its nearest double for non-integers.
- **(b) The survey's shortest round-trip rule.** `0.10000000000000001` is flagged. Files from producers that print 17 digits raise
  many issues.

## Decision

(a). Values in the value view are plain doubles (survey option D). A number is a structural error when its value is an integer
and the double differs from it, when it overflows, or when a non-zero value underflows to zero. A fractional number with more
digits than a double holds is accepted and means its nearest double. `-0` is 0. Integers stay exact up to ±(2^53−1), and vmd
writes larger int64 and bigint values as strings, as decided earlier. No edit rewrites a number it did not change.

## Why

The card's reason: it follows the owner's reasoning that a fractional decimal has no true value to protect, while integers do.
On underflow, the owner holds that an error is justified because no reasonable serializer writes a non-zero double as a literal
that underflows to zero; the session confirmed that the smallest positive double is about 4.9e-324, which shortest-form
serializers print as `5e-324`. (b) flags many files from producers that print 17 digits.

## Owner's note

> "It is an error when a non-zero value underflows to zero (1e-400)": this is an interesting case, if we accept that numbers can
> be written in any representation and it gets rounded to nearest double, then if 1e-400 gets rounded to 0, then it's normal.
> On the other hand one could consider zero and non-zero double very different. However, the answer here comes from the
> question: Would any reasonable serializer that serializes non-zero double write a number like 1e-400 that underflows to zero?
> If not, then the case for erroring on it is fairly strong.

## Applied in

Draft v0.4 (#50, `1043a6c`), §4.2. [G1](G1.md), from the review of #50, decided that a number is an integer by its form, not its
value, so that `1e23` means its nearest double.
