## Question

Options (a) and (b) of [C4](C4.md) both need a rule for which numbers a double holds faithfully. The survey proposed that a
number is double-safe when its decimal value equals the shortest decimal that gives back the same double, and named a weaker
alternative (survey §5.2 and §5.5). For example, `0.10000000000000001` has 17 significant digits and the same nearest double
as `0.1`: under the proposed rule it is exact-only, under the weaker rule it is safe and equal to `0.1`. Digit count alone does
not decide: `9007199254740993` has 16 digits and is exact-only, while `100000000000000000000` has 21 and is safe. The rule also
makes `1e-400` exact-only, since a double rounds it to 0.

## Options

- **(a) Shortest round trip (the survey's rule).** Recommended. A number is safe only if nothing is lost, which keeps §4.2's
  sentence that a number's meaning is its decimal value. Files from tools that print 17 significant digits (`printf "%.17g"`)
  are flagged often, so under C4 (a) such a producer's files raise many issues until it is configured to print the shortest
  form.
- **(b) Survives 17 significant digits.** Anything that goes to a double and back through 17 digits is safe, so
  `0.10000000000000001` is accepted and silently equals `0.1`. Fewer issues on such files, but two different decimal values
  become one number, contradicting §4.2's definition of a number's meaning.

Chosen: neither. The owner answered Other, with the note below: integers that would lose precision are rejected, and a fractional
number that parses properly as a double is probably fine.

## Decision

The owner's own answer: for integers, reject numbers that would lose precision; for numbers with a fractional value, a number
that properly parses as a double is probably fine, since neither `0.10000000000000001` nor `0.1` is precise. The follow-up
[F2](F2.md) confirmed the combined rule.

## Why

The owner's reason: finding the shortest representation is not trivial, and it depends on how common it is for serializers to
pick it; a fractional decimal has no known true value, since rounding is lossy anyway, so choosing `0.10000000000000001` is not
really invalid. The card recommended (a), and argued against (b): "It keeps §4.2's definition intact. If a producer the
project must ingest writes 17-digit floats, the better remedy is option b of C4 (keep them exactly), not a weaker rule here."

## Owner's note

> oh my, I remember this problem from a decade ago. For integer numbers, we reject numbers that would lose precision. For
> numbers with fractional value, well, figuring out what the shortest representation of a number is, from what I remember is not
> trivial. For those numbers I think the answer depends on, how common it is for json serializers across languages to guarantee
> picking the shortest representation?
> But then also choosing a 0.10000000000000001 is not really invalid, neither this number or 0.1 is precise, and we don't
> actually know what the true value "is supposed" to be, as the rounding will be lossy anyway. So a number that properly parses
> as a double is probably fine. And who knows some overeager toString may print more than 17 significant digits, and the 18th
> could matter? Do we actually need to have a strong opinion on this? Is there a risk that different parsers would parse
> differently a longer double value?
