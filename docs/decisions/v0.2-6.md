## Question

Draft v0.2 keyed a section's subsections by their section keys, and gave a section with only text its text as its value. The owner
pointed out that Markdown may have duplicate section names, which do not resolve cleanly by path, and asked whether sections
should always be an array, with duplicates handled by a resolution policy; and whether a plain string should count as a section.
The session also asked whether the root's single H1 becomes `$title`, for uniformity with sections, or stays a `title` field.

## Options

- **(a) Draft v0.2's model.** Sections keyed by their keys in an object; a section with only text has its text as its value, and
  becomes an object when it gains a subsection or a data block; the single H1 is a `title` field.
- **(b) A record is a section, with `$sections` an ordered array.** Chosen, from the owner's proposal as the session worked it out.
  Every record and section has one shape; Markdown to JSON is total and lossless, keeping order and duplicates; the H1 is the
  root's `$title`.

## Decision

(b). Every record and section has the shape `{ $title?, $anchor?, $tags?, ...fields, $body?, $sections?: [section, ...] }`. Front
matter is the root's data block. The single leading H1 is the root's `$title`; otherwise H1s are ordinary sections. Sections are
an ordered array, which keeps order and duplicates. A plain string is never a section; every value that is not a section item is
a field in the data block. Markdown to JSON is total and lossless; JSON to Markdown is total.

## Why

The owner's reasons: duplicate section names do not resolve cleanly as object keys, and an array keeps every section uniquely
identifiable while name-based paths still work. The session's reasons against (a): (b) removes Draft v0.2's collision rule, the
digit-only-key problem and the plain-title machinery, and the wart that a section's value changed from a string to an object when
it gained a subsection, which broke schemas and queries. Its stated costs: equivalence moves from values to addresses, JSON Schema
over an array of sections is clumsy (answered by keyed lists, [v0.2-9](v0.2-9.md)), and the root title moves to `$title`, which
the owner accepted.

## Owner's note

> Point 4: "its subsections: headings of a deeper level, keyed by their section keys". That may not always work. A markdown may
> have duplicate section names. Which may not resolve cleanly when addressing them by path. So perhaps sections should be just an
> array, always? Then each of them can always be uniquelly identified. The name-based paths would still work. A handling of
> duplicates when resolving by name would probably be a resoution policy.

> As for section representability, if we permitted yaml/json matter at front of each section, then a json document could also
> be plopped there as --- --- delimited section contents. So perhaps we would not consider a simple text as section
> representable. And instead require a proper form like {name: "blah", $body: "blah blah"}, and if not, it would just get inlined
> into parent section as key-value entry in the json/yaml front matter-like header.

> Agreed on H1 mapping to $title, same as any other section, if we can get away with it.
