## Question

With sections an ordered array ([v0.2-6](v0.2-6.md)), how does an address reach a node? The owner distinguished an exact path,
strictly by key names and array indexes (`abc/0/value`), from a semantic resolution in which a step is a field name or an array
item with a key field (`abc/def`).

## Options

- **(a) Two kinds of path: exact and semantic.** Chosen, from the owner's proposal as the session worked it out. An exact path is
  an RFC 6901 JSON Pointer, precise but unstable when items are inserted; a semantic path is for people, references and queries.

Other options: Not recorded.

## Decision

(a).

- `#/...` is an RFC 6901 JSON Pointer, unchanged.
- `#a/b` is a semantic path. Each step matches a member name, a child section's `$key`, or an item of a keyed list. The first step
  also tries record-wide anchors, including GitHub's derived slugs.
- A section's `$key` is its `$anchor`, or the GitHub slug of its `$title`.

## Why

The owner's reason: a path-based resolver can support both object and array representations uniformly, with the exact path based
strictly on key names and array indexes, and the semantic path resolving a step as a field name or a keyed array item. The
session's reason for the first step trying record-wide anchors: a plain GitHub link such as `file.md#what-is-confirmed` still
reaches a nested heading.

## Owner's note

> This all touches the whole concept of storing key-value collections as object {key1:value1, ...} vs array [{key: "key1",
> value:value1}]. The secon is more appropriate where duplicates are possible and order matters (so it applies to markdown). A
> path-based resolver can support both cases uniformly. But this may bring distinction of exact path (based strictly on
> key-names/array-indices) vs semantic resolution. like a document {abc: [{key:"def", value: 123}]} would use exact path like
> abc/0/value to refer to the value 123, while semantic path would use abc/def where def would try to be resolved either as a
> field name, or array item with key field.
