## Question

The owner proposed adding "extensibility" to Draft v0.2's goals: support for custom backends and for custom query languages over
the defined data model, such as GraphQL. What does the specification need for that?

## Options

- **(a) Extensibility as a goal, with the data model specified on its own.** Chosen. In the session's answer: nodes, keys, values,
  references and versions defined independently of the CLI and VQL; query engines that receive a read-only snapshot and return
  node addresses with projected values, VQL being the built-in one; and writes from any language going through `apply`.

Other options: Not recorded.

## Decision

(a). Custom backends, and custom query languages over the data model (for example GraphQL). The data model is specified
independently of the CLI and VQL. Query engines plug in and read freely; writes from any engine go through `apply`, so version
tokens and validation hold.

## Why

The session's reason for routing writes through `apply`: it keeps version tokens and validation in force whatever the language;
a GraphQL mutation would compile to an `apply`. Why extensibility is a goal: the owner's proposal; no further reason recorded.
