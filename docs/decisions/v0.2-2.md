## Question

Draft v0.2 said: "Only top-level blocks of the document take part in the structure. Headings and fences inside block quotes, lists
or HTML blocks are body text." The owner asked how necessary that is: if the object model reasons over sections and over YAML or
JSON at the top level, it should also reason over properly fenced YAML or JSON inside a subsection. The session explained that
"top-level" meant CommonMark's container nesting, not section depth, so a data block under a `####` heading already works. Do
headings and fences inside list items, block quotes and HTML blocks take part in the structure?

## Options

- **(a) Blocks inside containers are prose.** Chosen. A section's data block must be a fence, since `---` inside a body is a
  thematic break or a setext heading.
- **(b) Headings and data blocks inside containers take part in the structure.**
- **(c) `---`-delimited data blocks inside a section**, as front matter is delimited. CommonMark reads `---` as a thematic break,
  and `key: v` followed by `---` becomes a level-2 heading; GitHub renders it that way.

## Decision

(a). Headings and fences inside list items, block quotes and HTML blocks are body text. A section's data block must be fenced
(```` ```yaml data ````): `---` inside a body is a thematic break or a setext heading, and renders as one.

## Why

The session's reasons against (b): a list item has no key, so a data block inside one has no unambiguous place in the tree;
fenced code inside list items is common for examples; and a heading inside a block quote is usually quoted material, not
structure. Lists and tables can become addressable later through views. Against (c): CommonMark gives `---` other meanings, and
front matter works only because it sits at byte 0, where renderers special-case it.

## Owner's note

> 2) 43. Markdown "Only top-level blocks of the document take part in the structure. Headings and fences inside block quotes,
> lists or HTML blocks are body text.", how necessary the requirement of that is? If object model can reason over sections (which
> resemble nested fields perhaps?) and yaml/json at top level, then it should also be able to reason over the yaml/json that is
> properly fenced, but located inside of a subsection.
