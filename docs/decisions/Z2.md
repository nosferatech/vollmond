## Question

From the references pull request (#99). When an anchor or a title is renamed, `vmd rename` records an alias from the old name to
the new one ([F8](F8.md)), so links to the old name keep working. The I2 design follows an anchor alias one step only
(`docs/design/i2-validate.md`, section 5.5), so after two renames, `a` to `b` to `c`, a link to `#a` is dangling; chains appear as
soon as a heading is renamed twice. The review of #99 found a related case: an anchor alias recorded under a record's old path,
followed by a move of the record (`a.md` to `b.md`), leaves `a.md#old` dangling, because the anchor lookup uses only the final
path. Record aliases already follow chains, with a cycle guard. Should anchor aliases follow chains too?

The card also notes that the owner's caveat on F8 applies either way: a link committed after a rename may mean a new anchor that
reuses the old name, and the alias design (#48) has to resolve that; following chains asks the same question at each step.

## Options

- **(a) Follow anchor chains too.** Chosen, as recommended. The card: "Chains are followed to the end, the same way record aliases
  are; a cycle ends as dangling. The record's old paths count too, which fixes the move case. Draft v0.13 changes the design's
  one-step rule; suite cases for both."
- **(b) Keep one step.** The card: "A twice-renamed anchor breaks old links until `check --fix` rewrites them. The move case
  stays dangling."

## Decision

(a): an anchor alias is followed through chains, as record aliases are, and a cycle ends as dangling. The record's old paths
count, so an anchor alias recorded under a record's old path still applies after a move. This changes the I2 design's one-step
rule. F8's caveat stays open for #48.

**Agent's reading, confirmed by the owner on [W4](W4.md) (items 6 to 8) for the first three details; W4 too leaves the last two
to the alias design (#48).** Five details the card leaves open, which Draft v0.13 states as follows:

- The rule for record chains, which neither the card nor the earlier draft states: a record path follows the record aliases
  whose `from` is the path, from one alias to the next, until it reaches a path that exists, or one that no record alias has as
  its `from`. #99's code and its test "stop a record alias chain at its first live path" follow this rule, and the suite case
  `refs-record-chain-live-midway` pins it. §13.6 states it as the record half of "the same way record aliases are".
- An anchor chain likewise ends at the first name that is live, or at a name that no alias has as its `from`. The card's "to the
  end" is read that way; where a live anchor stands in the middle of a chain, the chain stops there, which is the same question
  as F8's caveat, left to #48. The suite case `refs-anchor-chain-live-midway` pins this reading.
- A record's old paths are the paths whose record aliases lead to it, so they count for a reference written with the record's
  current path too: `b.md#old` resolves through an anchor alias recorded under `a.md` once `a.md` has moved to `b.md`, as
  `a.md#old` does. The suite case `refs-anchor-alias-under-old-path` pins this reading.
- Which alias counts where several have the same old name, within a record and its old paths, is not decided here: §13.6 leaves
  it to #48, where #99 noted that the last line of the file wins today.
- Nor is an old path that a live record has again: whether an anchor alias recorded under it applies to that record, to the
  record that moved away from it, or to both. §13.6 leaves it to #48, with the owner's caveat on F8, since a name that a live node
  reuses is the same question.

## Why

The card's reason: "Old links shouldn't depend on how many times something was renamed, and record aliases already work this way.
The cost is bounded by the alias file's size."

Why (b) lost: Not recorded. The card's consequences for it: a twice-renamed anchor breaks old links until `check --fix` rewrites
them, and the move case stays dangling.
