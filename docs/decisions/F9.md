## Question

[C23](C23.md) asked what the writer does with the computed `$key` a program hands back after reading it. The session first
restated F9 with a read-modify-write example and three options: ignore the stale `$key` and report the changed key, reject a
`$key` that disagrees, or turn it into an anchor. The owner then asked whether a reader has to return `$key` at all. It does not:
`$key` went into the value view so that schemas, queries and programs could see section keys without implementing the slug rule
([F5](F5.md)) themselves, and derived facts can instead be kept next to the value, not inside it: `value`, exactly the stored
data, and `meta`, what vmd derives (key, address, anchors, node version, source lines). F9 was replaced with that question.
Should readers return the computed `$key` at all?

## Options

- **(a) Drop `$key` from the value; deliver it in meta.** Chosen, as recommended. Reads return stored data only, plus a metadata
  envelope. The C23 problem disappears: a written `$key` is an error, and no program writes one back by accident. Programs still
  get keys without implementing the slug rule, from meta, outline and query results.
- **(b) Keep `$key` in the value view.** Programs see keys inline. The writer then needs a rule for a stale `$key` in a write:
  ignore it and report the changed key, reject it, or turn it into an anchor.

## Decision

(a), superseding C23. Readers return the stored data as the value, and what vmd derives (the key, the canonical address,
anchors, the node version, the source location) in a metadata envelope next to it (§5.10). A `$key` in a write is an error,
which is safe because reads never contain one. Schemas key sections with `x-vmd-list` `keys: ["@key"]`, which the validator
computes internally, and VQL gains an `@key` pseudo-field. Node versions hash stored data only. Under [C17](C17.md),
`#done/$key` is no longer a step. The owner's escaped-identifier idea from C23 is recorded for VQL (#29).

## Why

The card's reason: it keeps one owner per fact; the file owns the data, vmd owns what it derives, and the two never mix in one
object. The session listed what it buys: a read round-trips exactly, so read-modify-write needs no special handling; a `$key`
arriving in a write can only be a mistake and stays an error (§5.4); YAML and JSON records no longer show a member that is not in
the file; node versions hash only stored data. (b) needs a rule for a stale `$key` in every write.
