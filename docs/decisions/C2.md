## Question

§5.8 said every Markdown record has a value view, yet §5.3, §5.4 and §8.1 define errors inside records, such as a data block
right after the title heading, a member beginning with `$` where none is allowed, or a `$ref` object with other members. Is such
a record unreadable, or readable with an issue attached (suite question 2)? For example, a ticket has a `yaml data` fence
directly under its `# Title` line: under one reading `vmd get` on it fails and the ticket disappears from queries; under the
other, `vmd get` works, the misplaced block is reported as an error, and `vmd check` exits with code 4. A second part is
completeness (suite question 3): the suite compares the whole set of issues that check reports, so a check that stops at the
first error cannot pass a fixture that expects three.

## Options

- **(a) Fail only without a value view; check reports everything.** Recommended. Parse fails only for syntax errors and values
  outside the data model (§4.1), such as a YAML alias. Every other error is an issue attached to a readable value view, and the
  code list (C1) marks which codes are which. Check reports every issue it can find and exits with 4 on any error, while parse
  may stop at its first, so each failing parse fixture holds exactly one error. Invalid records stay visible in queries and the
  index, as §9.4 already requires.
- **(b) Any error fails parse.** Chosen. One simple rule, but a single misplaced data block makes a whole ticket unreadable to
  agents and drops it from query results. That contradicts §5.8 (Markdown to value view is total) and §9.4 (invalid records are
  indexed with their issues).
- **(c) Check may stop at the first error.** Implementations get slightly simpler, but fixtures can test only one issue per
  record, an agent repairing a file sees one problem per run, and which error counts as first would itself need a rule.

## Decision

(b), with the owner's note: any error fails parse, and parse and check still report every error they can find, "so that less
roundtrips to fix them are needed".

## Why

The owner's reason: accepting errors at parse leads to a proliferation of bad data, as with old browsers that rendered invalid
HTML; vmd should be strict, since there is a validator, and the backend or the submitters should reject malformed data. The
card recommended (a), to keep §5.8's promise that every record is readable and give agents the full list of problems in one run.
Why (c) lost: the owner asked for every error to be reported.

## Owner's note

> Accepting errors due to parse is a nice idea, but unfortunately it then often results in proliferation of bad data (like how
> old browsers accepted invalid html and did their best to render it, which resulted in all websites basically being
> malformed, and fixing those errors in a different way.  I think we should be strict. There is a validator, so the backend (or
> submitters) should reject malformed data. If they don't validate, they deserve a failed parse.  We should still report all
> errors if we can, so that less roundtrips to fix them it are needed
