## Question

The session asked what a semantic step does on a field and a section with the same key at one level (front matter `status` and
`## Status`), leaning towards an error. The owner saw it as the same question as items of an array with the same key, a UNIQUE
constraint, and listed the outcomes worth considering.

## Options

- **(a) An error**, and a validation error when used in an anchor. Chosen, as the default in strict mode.
- **(b) It resolves to the first occurrence**, a field name for example taking precedence ("first wins").
- **(c) It resolves to all occurrences**, where the context permits. Kept for selectors and lenient mode.

The owner also asked whether this is a store policy, a schema policy or a kind of anchor, and proposed a strict default that the
configuration can relax to warnings.

## Decision

(a), in layers.

- Field names and keyed-list keys share one namespace per level, so a front matter `status` and a `## Status` section are
  duplicates, as two `## Notes` sections are.
- Uniqueness is declared per list in the schema (`map` or `multimap`), with a store default for undeclared levels: `strict` by
  default (duplicates are validation errors), `lenient` as a relaxation (warnings; `ambiguous` only where a singular address is
  used).
- A singular address must cross only unique levels, which the checker verifies before evaluation. A reference that may resolve to
  several nodes says so: `x-vmd-ref: {cardinality: many}`.
- "First occurrence wins" is not a policy. GitHub's derived slugs (`#notes`, `#notes-1`) are unique by construction and still
  apply. Escape hatches for ingesting messy data that cannot be cleaned up may be added later; they are not normal operation.

## Why

The owner's reasons: it is a UNIQUE constraint, and if an anchor is treated as a foreign key, the query interpreter should know at
compile time that it is unique; a non-unique foreign key should use a different form that permits it explicitly; strict validation
should be the default, relaxable in the configuration. The session's reason against (b): with it, a stored reference silently
retargets when someone inserts an earlier duplicate, which is exactly the failure strict mode exists to prevent; an explicit
"first" can be written at the point of use with an exact path or a selector.

## Owner's note

> re "1.A field and a section with the same key at one level (front matter status and ## Status).", I'd expect that trying to
> resolve a conflict of field vs array item with a key, is similar to resolving when conflicting items in an array have the same
> key. The outcomes I think worth considering are:
> a) it's an error (and validation error when using in an anchor)
> b) it resolves to the first occurence. (a field name for example taking precedence)
> c) resolve to all occurences. (if context permits)
> That could be a store policy. Or a schema policy? It's basically a UNIQUE contraint. Or can be an anchor type? If we treat
> anchor as foreign key, then ideally we want to deal with unique keys there, and be able to know at "query compile" time that it
> is unique. However, a non-unique foreign keys may be useful, but I guess I'd then suggest using a little bit different anchor
> that explicitly permits it, so that query interpeter knows that it resolves to array of nodes not a single node.
> Then there is a question what would be a sensible default? I'd suggest a strict validation mode to be the default mode, that
> can be relaxed in the config and possibly then just issue warnings.

> 1. ok, lets drop the "first wins" for now. I expect that some escape hatches may be needed if someone really needs to enable
> ingesting junky data and making some sense of it, and may not have ability to modify/clean it up. But that should not be normal
> operation. But we can solve that later if need be.
