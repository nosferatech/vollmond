## Question

[F2](F2.md) says a number means its nearest double, and that it is an error when its value is an integer the double does not
hold. Read by value, `1e23` is an error, because the double nearest 10^23 is 99999999999999991611392, while `1e21` is fine, and
ordinary output of Python's `json.dumps`, such as `1e+23` or `1.152921504606847e+18`, is rejected too. Worse, vmd's own
canonical writer (shortest digits, no fraction for integers) would write the double 2^60 as `1152921504606847000`, an integer the
double does not hold, which its own parser then rejects, breaking the round trip for values vmd itself produced. The independent
review of #50 (Draft v0.4) found this blocking. Is a number an integer by its value, or by how it is written?

## Options

- **(a) By form: an integer is written without fraction or exponent.** Chosen, as recommended. Only plain digit strings (and
  YAML's integer forms) must be exact, so `9007199254740993` and `1152921504606847000` are errors while `1e23` and
  `1.152921504606847e18` are floats meaning their nearest double. vmd's writer emits integer-valued doubles beyond 2^53 in
  exponent form, so it never writes what it rejects. JavaScript's `JSON.stringify` output for doubles between 2^53 and 1e21
  (plain digits) is rejected, which protects ids written by JavaScript tools by mistake.
- **(b) By value: any integer-valued number must be exact.** `1e23` and Python's `1e+23` are errors, and the only acceptable form
  of a large double such as `1e300` is its 301-digit exact expansion, which the writer must emit. Simple to state, harsh in
  practice.

## Decision

(a). A number is an integer for the check of §4.2 when it is written as one, with no fraction and no exponent, so `1e23` means
its nearest double. vmd's writer emits integer-valued doubles beyond ±(2^53−1) in exponent form, so its own output always parses
back; the canonical writer uses exponent form exactly when |x| ≥ 2^53 or 0 < |x| < 10^-6 (§4.2). The round-trip property tests
include such values, and the suite has example cases for 2^60. As an application of G1, not a new decision, an integer by form
is any integer literal of its format, so a YAML `+9007199254740993` or `0x20000000000001` that a double cannot hold is an error
as a JSON one is, since precision lost while parsing must be flagged ([C4](C4.md)); the session extended the rule to YAML from
the owner's C4 note.

## Why

The card's reason: it matches the owner's reasoning in F2, that integers written as integers have a true value to protect, while
anything written as a float has no true value beyond its double. (b) is simple to state but harsh in practice: it rejects
ordinary serializer output and makes the writer emit exact expansions hundreds of digits long. The session named the cost of
(a): a plain `JSON.stringify` writes 2^60 as `1152921504606847000`, which vmd rejects.
