## Question

Draft v0.3's §4.1 promised that the order of an object's members is preserved. Should it?

## Options

- **(a) Preserve member order**, as the draft promised.
- **(b) Member order is not significant.** Chosen, by the owner. A backend that stores the original bytes keeps their order, but
  nothing may depend on it.

## Decision

(b). Object member order is not significant. A backend that stores original bytes keeps their order, but no backend or query may
be required to: covering indexes and relational stores have no original order to return. Order that matters uses arrays.

## Why

The owner's reason against (a): a backend may not store the original form; reading from a covering index or a relational database
has no original field order, and promising it forces a query to fetch the original document just to return fields in order, a
decision MongoDB made a decade ago that still causes trouble. The session noted that sections are an array, so a document's
section order and repeated headings are still kept.

## Owner's note

> in 4.1, I'd not promise that order is preserved. If data is stored in the original form (which it may or may not, that is
> backend dependent) then original bytes and order will be preserved. However, backend (and query language) can decide to reorder
> the fields as appropriate. Like when reading data back from a covering index, original field order may not be available. Or if
> data is stored in a relational database, then the original field order also will not be available. (This is actually one of
> decisions MongoDB made decade ago, that is still causing trouble, where queries are not always at liberty to use jsut covering
> secondary index, and instead need to fetch original document just to return data with fields in original order)
