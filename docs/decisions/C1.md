## Question

Every fixture that expects an error or a warning names it by a short code, such as `ref-ambiguous`, together with a severity
and the node it is attached to. The spec defined no codes yet; §12.3 showed `ref-ambiguous` only as an example, so no fixture
that expects an issue could be written in its final form (suite question 1). For example, a YAML file containing the alias
`b: *a` must be rejected, and its fixture expects `{code: "yaml-alias", severity: "error", path: "aliases.yaml", at: "/b"}`;
every implementation must print that same code, because the CLI prints it and the index stores it, and messages are never
compared. The severity also depends on the mode, and the list must say which codes stop a record from having a value view (C2).
Who defines issue codes and severities, and when?

## Options

- **(a) A spec appendix, grown by the fixtures.** Chosen, as recommended. A new appendix lists each code with its severity per
  mode, the section that raises it, the node it attaches to, and whether it prevents a value view. The fixture tasks (#5 to #7)
  propose codes as they need them, and I0.8 (#9) adopts them into the appendix, so fixtures can be written now. Severities are
  error and warning; a third one, such as info, can be added later without changing any existing fixture.
- **(b) The full list first, then fixtures.** The list is written before any fixture, so fixtures never have to be renamed. #5
  to #7 wait for it, and a list written without the cases in front of it tends to miss codes that are needed and to invent codes
  nothing raises.
- **(c) The suite keeps its own codes.** Fixtures can be written immediately with suite-only codes. The CLI and the index would
  then use a second vocabulary for the same issues, and the two drift apart. The suite README already rejects this.

## Decision

(a). A normative appendix of issue codes and severities (Appendix D), grown by the fixture tasks and adopted into the spec in
I0.8 and later rounds. The severities are `error` and `warning`.

## Why

The card's reason: as the suite recommends, it unblocks the fixture tasks now, and the cost of a renamed code is a search and
replace inside the suite. The card's consequences for the other options, not reasons it gives against them: (b) delays the
fixtures and tends to miss or invent codes; (c) gives the CLI and the index a second vocabulary that drifts from the suite's,
which the suite README already rejects.

## Applied in

Draft v0.4 (#50, `1043a6c`), Appendix D, which later rounds extend.
