## Question

The owner's note on card P (see [P3](P3.md)) asked what vmd does with comments in JSON blocks and files, and said it would be nice
to permit them. Today a `.json` record and a `json data` block are strict JSON (RFC 8259), and a comment is a `syntax-error`.
Allowing comments has three costs. Other tools: `JSON.parse`, `jq`, Python's `json` and most editors' JSON mode reject a `.json`
file with comments, and §1's goal 2 says every construct vmd reads "is already idiomatic in its format" and "needs no vmd tooling
to read". Versioning: under [U21](U21.md), relaxing a structural error is a valid minor addition, but a new file extension such
as `.jsonc` is not detectable by itself, because an older reader would take `notes.jsonc` for an asset rather than refuse it, so a
new extension needs a configuration member that turns it on. Writes (I4): `vmd set` must keep comments when it edits a value.
None of the options changes values, canonical forms or addresses: comments are not data. Are comments allowed in JSON records
and data blocks?

## Options

- **(a) Opt-in JSONC: `jsonc data` blocks and `.jsonc` files.** Chosen, as recommended. `.json` and `json data` stay strict, so
  other tools never meet comments there. A `jsonc data` info string (an allowed addition form) and `.jsonc` record files, the
  latter enabled by a configuration member, accept `//` and `/* */` comments (no trailing commas). Spec in a later draft; code
  after I2, with I4's comment-preserving edits.
- **(b) Comments allowed in every `.json` and `json data`.** Simplest for authors, and a valid minor addition. But a vmd store's
  `.json` files then stop being JSON for every other tool, without a visible sign.
- **(c) No comments.** Keep strict JSON, and use YAML, which has comments, where comments matter.

## Decision

(a): comments in JSON are opt-in, as `jsonc data` blocks and `.jsonc` record files enabled by a configuration member, accepting
`//` and `/* */` comments and no trailing commas. `.json` records and `json data` blocks stay strict JSON.

## Why

The card's reason: (a) gives comments to those who want them, keeps `.json` honest for other tools, and stays detectable for
older readers. Against (b), the card's consequence: a store's `.json` files stop being JSON for every other tool, without a
visible sign. The owner's reason for wanting comments at all, against (c): when machines talk JSON they write no comments, so
comments cost them nothing, while humans and agents working with JSON files such as configuration files gain a place to
document the reason for a setting.

## Owner's note

> I agree. I personally believe that json format not providing comments from the start was a mistake, as when machines talk json
> they wont write comments, so it costs them nothing. But when humans or agents want to work with json files (like config files)
> being able to document a reason for settings is very valueable. A json vs jsonc is a good compromise here.
