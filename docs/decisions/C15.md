## Question

GitHub's slug depends on its HTML sanitizer, which nobody documents: the text inside a `span` or `b` element counts, an unknown
tag vanishes, and `<script>alert(1)</script>` is kept as literal text, so `scriptalert1script` enters the slug. Reproducing this
exactly means copying GitHub's sanitizer and tracking its changes (slug report, item 1). For example,
`## Press <kbd>Ctrl</kbd> twice` gives `press-ctrl-twice` on GitHub. Should vmd promise that anchor, warn about the `kbd` element,
or both? Which HTML may a heading contain?

## Options

- **(a) Only the anchor element.** The trailing `<a id class></a>` element is the only HTML vmd supports in a heading. Any other
  HTML gets a strict-mode warning, and vmd makes no promise that the derived anchor matches GitHub's. The smallest rule, but
  harmless markup such as `<kbd>` or `<sup>` is warned about too.
- **(b) The anchor element plus a short list of inline elements.** Chosen, as recommended. Besides the anchor element, `span`,
  `b`, `i`, `em`, `strong`, `code`, `kbd`, `sup` and `sub` are supported, and their text counts as it does on GitHub, with
  fixtures for each. Other HTML gets a strict-mode warning with no promise. Covers what authors actually write, and the list is
  small enough to keep in fixtures.
- **(c) Follow GitHub's sanitizer.** No warnings, and fixtures track GitHub's behavior, including script and unclosed tags. The
  most faithful, but vmd must copy rules nobody documents, and a sanitizer change on GitHub's side breaks fixtures for markup no
  one should write in a heading.

## Decision

(b), with the owner's note. A heading may contain the anchor element plus `span`, `b`, `i`, `em`, `strong`, `code`, `kbd`, `sup`
and `sub`. Other tags are undefined behavior: a warning, or an error in the strictest configuration, which under [F1](F1.md) is
a validation error, so the record stays readable, and they may be stripped from the derived anchor.

## Why

The card's reason: the report suggested pinning a subset but named no list, and (b) is the session's middle ground; choose (a)
if the list should grow from real use rather than be guessed. (c) copies undocumented rules and breaks with GitHub's changes. The
strictest-mode error raised the follow-up F1, so that one unsupported tag does not make a whole document unreadable.

## Owner's note

> All unsupported tags, can be considered undefined behavior, flagged as warning or error (if a strictest mode is used) and who
> knows they may get stripped away from the anchor id.
