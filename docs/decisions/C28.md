## Question

§14.3 said the local index's storage engine is an implementation choice and named SQLite as the reference. The implementation
plan (§1.2) chose JSONL files instead, the same format as the portable index (§14.4), to avoid native dependencies, and brings
SQLite back only if measurements ask for it. The two documents disagreed. For example, an agent runs `npx @vollmond/cli` in a
fresh sandbox: with JSONL it installs anywhere Node runs; with SQLite it needs a native module or a WebAssembly build.

## Options

- **(a) JSONL, and §14.3 changes.** Chosen, as recommended. §14.3 keeps "implementation choice" and says the reference
  implementation uses JSONL files in the portable index's format. No native modules, and one format for local and published
  indexes. A large store's index may be slower to query until measured, at which point SQLite can return.
- **(b) SQLite, and the plan changes.** The CLI depends on a native SQLite module or a WebAssembly build, which complicates
  installation and the browser build, and the local and published indexes use two formats.

## Decision

(a). The local index uses JSONL, as the implementation plan chose, and §14.3 no longer names SQLite as the reference.

## Why

The card's reason: the plan's choice is the later and more considered one; §16.1's idea of a SQLite build for a query service is
unaffected. The card's consequence for (b), not a reason it gives against it: it complicates installation and the browser build
and gives two index formats.
